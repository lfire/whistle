# 抓包调试的能力模型

前三篇解释了流量「长什么样」：代理的形态、[TLS](/concepts/03-tls) 的信任链、HTTP/2 与 WebSocket 的[帧](/concepts/05-capture)结构。本篇换一个视角：一个调试代理到底要提供哪些能力，才能把一个模糊的线上问题收敛成可验证的结论。读完再进入架构篇，你会知道每个模块存在的理由，而不只是记住它的文件名。 承接 02–04 的领域结论，本篇不再新增协议细节，而是把它们翻译成「调试代理该有哪些能力」，为后面的架构篇预备每个模块存在的理由。

## 调试代理解决的矛盾

联调与排障时常常同时受三个约束：**不能改业务代码**（改了就不是原来的现场）、**不能停服务**（问题只在特定流量下出现）、**要能控制输入**（构造平时造不出来的响应）。浏览器 DevTools 只能看到自己这一页，服务端日志看不到客户端发出的原始报文，单元测试又脱离了真实链路——代理恰好卡在客户端与服务器之间，是唯一能同时「看见两端」并「动手改写」的位置。

Whistle 把自己定位成「基于 Node.js 的跨平台网络[抓包](/concepts/05-capture)与调试工具」（`README.md:17-29`），但真正让它从「能看」变成「能改」的，是规则配置这一层：`README.md:23` 直接把「通过规则配置即可修改请求/响应」列为操作简单的核心。因此读源码时可以把整个工程理解为两件事——**把流量变成可观察、可干预的对象**，以及**让「什么时候干预、怎么干预」可以被文本描述**。

**为什么这样设计**：联调时「不能改业务代码、不能停服务、要能控制输入」三个约束同时成立，才逼出了「代理」这个位置——浏览器 DevTools 只看得到自己这一页，服务端日志看不到客户端原始报文，单元测试又脱离真实链路，只有卡在两端之间的代理能同时「看见两端」并「动手改写」。把「规则配置这一层」的结论展开成推理：能看见只是把流量变成可观察对象，能干预还要让「什么时候干预、怎么干预」可被文本描述；少了后者，每次实验都得改代码，现场就不复存在了。

**代价与边界**：代价是代理成了链路上的一个新环节，本身也会有性能开销与单点风险；边界是它只在你有权调试的流量上成立，生产治理并不适合交给它。因此读整个工程时，把它理解成两件事最省力：把流量变成可观察、可干预的对象，以及让干预策略可以被文本描述。

**打个比方**：像在不打断演出前提下的舞台监督——既能看到台上与后台，又能临时递台词，却不许改剧本、不许停演；规则配置就是那本可随时改写的提示册。

**自己验证**：对照三个约束逐条问自己「DevTools、服务端日志、单元测试各缺哪一个」，会发现它们各缺一块、只有代理三样都占；这一步不用跑任何命令，就能验证「为什么非得是代理」。

## 七类能力

把 Whistle 的功能按「对流量做了什么」归类，会得到一张很稳定的能力表。后续所有模块都能在这张表里找到自己的位置。

::: cols 16|34|50
| 能力 | 回答的问题 | 实现落点 |
|---|---|---|
| 观察 | 实际发了什么、回了什么 | `inspectors/data.js`、`util/data-server.js` |
| 匹配 | 这条规则管哪些请求 | `rules/rules.js` 的 pattern |
| 改写 | 头、体、状态码怎么改 | `inspectors/req.js`、`res.js` |
| 模拟 | 不请求真实后端 | `handlers/file-proxy.js` |
| 注入 | 往页面/响应里加东西 | `res.js` 的 `*Append`、`inspectors/weinre.js` |
| 编排 | 多条规则如何叠加 | `rules/util.js`、Storage |
| 扩展 | 内置能力不够怎么办 | `plugins/`、`handlers/http-proxy.js` |
:::

「观察」是其余六类的地基：只有先把请求与响应采集成结构化对象并附上 `reqId`，才能在 UI 里点开详情、按规则过滤、把某次请求重放到 Composer。`lib/inspectors/data.js:55` 起的 `emitDataEvents` 先保存原始 `stream.write` / `stream.end`，在 `:279-310`（请求体）与 `:364-388`（响应体）把它们覆写成「累加字节、超过 `maxReqSize` / `maxResSize` 就把 `reqBody` / `resBody` 置为 false，最后 `return write.apply(this, arguments)`」——采样走旁路，原转发链路不受影响。`lib/util/data-server.js:10-12` 把 `reqCacheSize` 的下限锁死在 600（CLI 对应 `-R/--reqCacheSize`，见 `docs/docs/cli.md:47`），由此推出 `MAX_LENGTH` 与溢出线 `OVERFLOW_LENGTH = MAX_LENGTH * 3`（`:21-23`）；`clearCache()`（`:147-201`）每 6 秒（`:18,94`）按 `CACHE_TIME` 2 分钟 / `MAX_CACHE_TIME` 6 分钟淘汰超时或溢出的会话。之所以不是全量缓存，是因为调试代理可能长期挂在一台开发机上，无上限缓存会先拖垮自己。

「匹配」与「改写」分离是关键设计。规则文本被编译成按协议分桶的结构（`lib/rules/rules.js:1745-1806`），请求到来时先算出命中集合 `req.rules`（`:2239-2299`），再由各个 inspector 在合适的时机读取自己的那一项。这样新增一种改写能力，只需要新增协议名和对应的消费点，不必改动匹配算法；反过来，优化匹配性能也不会影响改写逻辑。

「模拟」是调试效率和真实度之间的旋钮。`handlers/file-proxy.js:233-269` 在本地协议命中时直接短路，请求根本不会打到网络；而 `proxy`、`host`、`rulesFile` 一类指令仍然走真实链路。理解这一点很重要：**一旦用了本地 mock，你验证的就不是后端行为，而是自己对后端行为的假设**。

**为什么这样设计**：把功能按「对流量做了什么」归类，是为了让后续每个模块都能在表里找到自己的位置；其中「观察」是地基——只有先把请求与响应采集成结构化对象并附上标识，才能在界面里点开详情、按规则过滤、把某次请求重放。把「采样走旁路」的结论展开成推理：保存原始写方法、再覆写成「累加字节、超限就置否、最后仍调用原方法」，意味着采集与转发是两条互不干扰的路；之所以不是全量缓存，是因为调试代理可能长期挂在一台开发机上，无上限缓存会先拖垮自己。

**匹配与改写为什么分离**：规则文本先编译成按协议分桶的结构、请求到来时算出命中集合，再由各 inspector 在合适时机读取自己的那一项；这样新增一种改写能力只需加协议名与消费点，不必改匹配算法，反之优化匹配性能也不影响改写逻辑。代价是「命中了什么」与「谁去执行」分处两地，排查「规则没生效」时必须先看最终命中集合，而不是凭规则文本猜。

**模拟为什么最容易误用**：本地协议命中时请求直接短路、根本不打网络，而 `proxy`、`host`、`rulesFile` 一类指令仍走真实链路。把这句结论展开成推理：一旦用了本地 mock，你验证的就不是后端行为，而是自己对后端行为的假设；假设错了，测试再绿也没意义。

**打个比方**：七类能力像一间工具间，观察是灯、匹配是标签、改写是扳手、模拟是替身演员；没有灯，后面六样都不知道该往哪使劲。

**自己验证**：在 Network 界面确认一次请求可见、再到 Rules 里看它命中了哪条，就能亲手验证「观察 → 匹配」这条地基关系，也正好预告了下一节四步里的前两步。

## 一次典型排障的四步

1. **复现与观察**：挂上代理、确认能看到目标请求，先只读不改。此时要留意 [CONNECT](/concepts/01-proxy) 是否已被解密——`lib/tunnel.js:168-213` 的判定会让部分系统域名始终透传，看不到明文不代表没抓到。
2. **缩小范围**：用 pattern 把规则限定到具体域名与路径，配合 `includeFilter` / `excludeFilter` 只影响符合条件的请求（`lib/rules/rules.js:1549-1739`）。范围越窄，越不会污染同事或自己的其它页面。
3. **构造反例**：先用 `resBody` / `statusCode` 假设「如果后端返回 500 会怎样」，再用 `reqDelay` / `resSpeed` 假设「如果网络慢三秒会怎样」。这类实验的价值在于把偶发问题变成必现问题。
4. **验证与清理**：确认修复后，务必关闭或删除规则。Whistle 用规则集与 `selectedList` 管理启用的规则（`lib/rules/util.js:198-208`），但「忘了关」依然是实践中最常见的坑——建议把实验规则放在独立规则集，用完整体取消选中。

这四步对应到界面就是 Network、Rules、[Values](/concepts/06-rules)、Plugins 四个 Tab（`biz/webui/htdocs/src/js/index.js:75`）：观察在 Network，编排在 Rules，大段 mock 内容放 Values，能力不够时写[插件](/concepts/07-extension)。

**为什么这样设计**：四步按「复现与观察 → 缩小范围 → 构造反例 → 验证与清理」推进，是因为排障最怕同时改动太多：先只读不改确认现场，再用 pattern 把规则限定到具体域名与路径，避免污染同事或自己的其它页面。把「构造反例」的价值展开成推理：偶发问题难查，是因为它不总出现；用 `resBody` / `statusCode` 假设「后端返回 500」、用 `reqDelay` / `resSpeed` 假设「网络慢三秒」，等于把偶发条件人为固定下来，问题就从「偶尔」变成「必现」。

**代价与边界**：代价是实验规则本身就是对现场的干预，忘了关就会一直改写流量——文档点明「忘了关」是实践中最常见的坑，建议把实验规则放在独立规则集、用完整体取消选中。边界是：清理这一步不是收尾礼貌，而是保证结论可信的前提，否则你验证的是被规则改过的系统。

**打个比方**：像医生做激发试验——先记录基础体征，再只施加一个可控刺激观察反应，最后把刺激撤掉确认恢复；不撤刺激，就分不清好转是药效还是刺激未退。

**自己验证**：按 Network、Rules、Values、Plugins 四个 Tab 把四步各归一位——观察在 Network、编排在 Rules、大段 mock 内容放 Values、能力不够时写插件；能对上号，就说明这套方法论与界面是一一对应的，而不是抽象口号。

## 规则编排为什么容易踩坑

规则是文本，但它不是无状态的配置文件。至少有三个隐含状态需要在动手前想清楚：

::: cols 22|38|40
| 隐含状态 | 表现 | 排查入口 |
|---|---|---|
| 顺序 | 同协议首条命中生效 | `rules/rules.js:997` |
| 作用域 | 规则集、插件规则叠加 | `rules/util.js:71-104` |
| 时机 | 请求期与响应期分离 | `rules/protocols.js:155-161` |
:::

「顺序」意味着把一条宽泛的 `*.example.com` 写在前面，后面的精确规则可能永远不生效；`lineProps://important` 与 `backRulesFirst` 又提供了两种改变顺序的方式——后者的实现就在 `lib/rules/util.js:74-79`，它把后台规则 `unshift` 进 `rulesList` 头部，等价于整批插到最前，所以「顺序」本质是规则列表的拼接次序。「作用域」意味着你看不到的一条插件规则可能正在改写同一个头。「时机」意味着 `reqHeaders` 与 `resHeaders` 虽然名字对称，却分别在不同 inspector 里执行，不能互相覆盖。这三类问题的共同解法不是猜，而是先看 `req.rules` 最终命中了什么——UI 的「匹配的规则」入口正是由此而来（`biz/webui/cgi-bin/get-matched-rules.js`）。

**为什么这样设计**：规则是文本，却带着顺序、作用域、时机三个隐含状态，所以「改了规则没反应」往往不是语法错、而是状态没对上。把三者展开成推理：顺序意味着把一条宽泛的 `*.example.com` 写在前面，后面的精确规则可能永远不生效，`lineProps://important` 与 `backRulesFirst` 都只是在改变规则列表的拼接次序；作用域意味着你看不到的一条插件规则可能正在改写同一个头；时机意味着 `reqHeaders` 与 `resHeaders` 名字虽对称，却分处不同 inspector、不能互相覆盖。

**代价与边界**：代价是规则文本读起来无状态、行为却有状态，光看字面推不出结果；边界是这三类问题都没有「猜」的捷径，共同解法是先看最终命中集合，UI 的「匹配的规则」入口正是由此而来。

**打个比方**：像同时叠了几张透明胶片，每张都改一点颜色，单看任一张都对、叠起来却偏色；想核对只能看最终叠出来的那张，而不是逐张猜。

**自己验证**：遇到「规则没生效」，先去界面看「匹配的规则」返回了什么，再回头对照顺序、作用域、时机三项；这个顺序正是把隐含状态显式化的最短路径。

## 能力边界

调试代理不是万能的，知道它做不到什么，比记住多少指令更重要。

| 场景 | 为什么难 | 更合适的手段 |
|---|---|---|
| 证书固定 / mTLS | 客户端不信任伪造证书 | 客户端日志、服务端埋点 |
| 二进制私有协议 | 没有 HTTP 语义 | 专用解析器插件、tcpdump |
| 需要长期生效的契约 | 规则易被忘记关闭 | 契约测试、接口测试 |
| 生产流量治理 | 代理是单点且有性能开销 | 网关、Service Mesh |

还有一个边界是合规：代理能看到明文意味着它能看到 Cookie、令牌与个人信息。中间人解密只应作用于自己有权调试的流量，采集到的会话应视为敏感数据处理，不要在共享环境长期留存。

**为什么这样设计**：把「做不到什么」单独列成表，是因为知道边界比记住多少指令更重要——证书固定 / mTLS 时客户端不信任伪造证书，二进制私有协议没有 HTTP 语义，长期生效的契约会被「忘了关」破坏，生产流量治理又嫌代理是单点且有性能开销。把每一行的「更合适的手段」展开成推理：客户端日志与服务端埋点不依赖换证书，专用解析器插件或 tcpdump 不需要 HTTP 语义，契约测试与接口测试不靠人记得关规则，网关与 Service Mesh 本就是为长期治理设计的。

**代价与边界**：还有一层看不见的边界是合规——代理能看到明文，就意味着能看到 Cookie、令牌与个人信息；中间人解密只应作用于自己有权调试的流量，采集到的会话应视为敏感数据处理，不要在共享环境长期留存。换句话说，能力越强，越要主动划清「不做什么」。

**打个比方**：调试代理像一把可调的万能扳手，适合现场临时拧几下；真要长期固定一台机器，还是得换专用工装，而不是让扳手一直卡在管路上。

**自己验证**：对照边界表问自己「这条需求会不会长期生效、要不要动他人流量」；只要有一个答「是」，就该把它交给契约测试或网关，而不是继续加规则。

## 常见误解

1. **容易以为用了本地 mock 就验证了后端行为，其实验证的是自己对后端的假设**：本地协议命中时请求直接短路、根本不会打到网络，而 `proxy`、`host`、`rulesFile` 一类指令仍走真实链路，对照见[《易混淆概念辨析》](/concepts/08-confusions)。
2. **容易以为「看不到明文」等于「没抓到」，其实解密判定会让部分系统域名始终透传**：排障第一步要先确认 CONNECT 是否已被解密，透传条目不代表抓包失败。
3. **容易以为 `reqHeaders` 与 `resHeaders` 名字对称就能互相覆盖，其实它们分处请求期与响应期、在不同 inspector 里执行**：顺序、作用域、时机这三个隐含状态，共同解法不是猜，而是先看最终命中集合。
4. **容易以为调试代理可以顺带做生产流量治理或长期契约，其实都不在它的舒适区**：代理是单点且有性能开销，规则又容易被忘记关闭，长期契约应交给契约测试与接口测试，生产治理交给网关或 Service Mesh。

## 小结

- 调试代理的核心价值是「在不改代码的前提下同时观察并干预两端流量」，规则层是它区别于纯抓包工具的关键。
- 七类能力中，观察是地基，匹配与改写分离是可扩展性的来源，模拟则是最容易误用的能力。
- 排障按「观察 → 缩小范围 → 构造反例 → 验证清理」推进，规则用完必须关掉。
- 顺序、作用域、时机是规则编排的三个隐含状态，遇到「规则没生效」优先查最终命中集合。
- 证书固定、私有协议、长期契约与生产流量治理都不属于调试代理的舒适区。
- 本篇为 [《一张图看懂全局架构》](/architecture/overview) 准备了七类能力的清单与排障四步：有了「每个模块该解决什么问题」的预期，06 把入口、中间件与事件总线拼成进程时才对得上号。
