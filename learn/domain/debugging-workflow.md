# 抓包调试的能力模型

前三个小节解释了流量「长什么样」：代理的形态、TLS 的信任链、HTTP/2 与 WebSocket 的帧结构。本篇换一个视角：一个调试代理到底要提供哪些能力，才能把一个模糊的线上问题收敛成可验证的结论。读完再进入架构篇，你会知道每个模块存在的理由，而不只是记住它的文件名。

::: tip 先修知识
了解 HTTP 请求/响应的基本结构，知道代理与证书的关系即可。本篇是方法论，不出现新的协议细节。
:::

## 调试代理解决的矛盾

联调与排障时常常同时受三个约束：**不能改业务代码**（改了就不是原来的现场）、**不能停服务**（问题只在特定流量下出现）、**要能控制输入**（构造平时造不出来的响应）。浏览器 DevTools 只能看到自己这一页，服务端日志看不到客户端发出的原始报文，单元测试又脱离了真实链路——代理恰好卡在客户端与服务器之间，是唯一能同时「看见两端」并「动手改写」的位置。

Whistle 把自己定位成「基于 Node.js 的跨平台网络抓包与调试工具」（`README.md:17-29`），但真正让它从「能看」变成「能改」的，是规则配置这一层：`README.md:23` 直接把「通过规则配置即可修改请求/响应」列为操作简单的核心。因此读源码时可以把整个工程理解为两件事——**把流量变成可观察、可干预的对象**，以及**让「什么时候干预、怎么干预」可以被文本描述**。

## 七类能力

把 Whistle 的功能按「对流量做了什么」归类，会得到一张很稳定的能力表。后续所有模块都能在这张表里找到自己的位置。

::: cols 16|34|50
| 能力 | 回答的问题 | 实现落点 |
|---|---|---|
| 观察 | 实际发了什么、回了什么 | `inspectors/data.js`、`util/data-server.js` |
| 匹配 | 这条规则管哪些请求 | `rules/rules.js` 的 pattern |
| 改写 | 头、体、状态码怎么改 | `inspectors/req.js`、`res.js` |
| 模拟 | 不请求真实后端 | `handlers/file-proxy.js` |
| 注入 | 往页面/响应里加东西 | `res.js` 的 `*Append`、`inspectors/weinre.js` |
| 编排 | 多条规则如何叠加 | `rules/util.js`、Storage |
| 扩展 | 内置能力不够怎么办 | `plugins/`、`handlers/http-proxy.js` |
:::

「观察」是其余六类的地基：只有先把请求与响应采集成结构化对象并附上 `reqId`，才能在 UI 里点开详情、按规则过滤、把某次请求重放到 Composer。`lib/inspectors/data.js:55-185` 通过包装流的 `write`/`end` 旁路采样，不阻塞转发；`lib/util/data-server.js:10-35` 用有界缓存保存最近若干条记录。之所以是「最近若干条」而不是全量，是因为调试代理可能长期挂在一台开发机上，无上限缓存会先拖垮自己。

「匹配」与「改写」分离是关键设计。规则文本被编译成按协议分桶的结构（`lib/rules/rules.js:1745-1806`），请求到来时先算出命中集合 `req.rules`（`:2239-2299`），再由各个 inspector 在合适的时机读取自己的那一项。这样新增一种改写能力，只需要新增协议名和对应的消费点，不必改动匹配算法；反过来，优化匹配性能也不会影响改写逻辑。

「模拟」是调试效率和真实度之间的旋钮。`handlers/file-proxy.js:233-269` 在本地协议命中时直接短路，请求根本不会打到网络；而 `proxy`、`host`、`rulesFile` 一类指令仍然走真实链路。理解这一点很重要：**一旦用了本地 mock，你验证的就不是后端行为，而是自己对后端行为的假设**。

## 一次典型排障的四步

1. **复现与观察**：挂上代理、确认能看到目标请求，先只读不改。此时要留意 CONNECT 是否已被解密——`lib/tunnel.js:168-213` 的判定会让部分系统域名始终透传，看不到明文不代表没抓到。
2. **缩小范围**：用 pattern 把规则限定到具体域名与路径，配合 `includeFilter` / `excludeFilter` 只影响符合条件的请求（`lib/rules/rules.js:1549-1739`）。范围越窄，越不会污染同事或自己的其它页面。
3. **构造反例**：先用 `resBody` / `statusCode` 假设「如果后端返回 500 会怎样」，再用 `reqDelay` / `resSpeed` 假设「如果网络慢三秒会怎样」。这类实验的价值在于把偶发问题变成必现问题。
4. **验证与清理**：确认修复后，务必关闭或删除规则。Whistle 用规则集与 `selectedList` 管理启用的规则（`lib/rules/util.js:198-208`），但「忘了关」依然是实践中最常见的坑——建议把实验规则放在独立规则集，用完整体取消选中。

这四步对应到界面就是 Network、Rules、Values、Plugins 四个 Tab（`biz/webui/htdocs/src/js/index.js:75`）：观察在 Network，编排在 Rules，大段 mock 内容放 Values，能力不够时写插件。

## 规则编排为什么容易踩坑

规则是文本，但它不是无状态的配置文件。至少有三个隐含状态需要在动手前想清楚：

::: cols 22|38|40
| 隐含状态 | 表现 | 排查入口 |
|---|---|---|
| 顺序 | 同协议首条命中生效 | `rules/rules.js:997` |
| 作用域 | 规则集、插件规则叠加 | `rules/util.js:71-104` |
| 时机 | 请求期与响应期分离 | `rules/protocols.js:155-161` |
:::

「顺序」意味着把一条宽泛的 `*.example.com` 写在前面，后面的精确规则可能永远不生效；`lineProps://important` 与 `backRulesFirst` 又提供了两种改变顺序的方式。「作用域」意味着你看不到的一条插件规则可能正在改写同一个头。「时机」意味着 `reqHeaders` 与 `resHeaders` 虽然名字对称，却分别在不同 inspector 里执行，不能互相覆盖。这三类问题的共同解法不是猜，而是先看 `req.rules` 最终命中了什么——UI 的「匹配的规则」入口正是由此而来（`biz/webui/cgi-bin/get-matched-rules.js`）。

## 能力边界

调试代理不是万能的，知道它做不到什么，比记住多少指令更重要。

| 场景 | 为什么难 | 更合适的手段 |
|---|---|---|
| 证书固定 / mTLS | 客户端不信任伪造证书 | 客户端日志、服务端埋点 |
| 二进制私有协议 | 没有 HTTP 语义 | 专用解析器插件、tcpdump |
| 需要长期生效的契约 | 规则易被忘记关闭 | 契约测试、接口测试 |
| 生产流量治理 | 代理是单点且有性能开销 | 网关、Service Mesh |

还有一个边界是合规：代理能看到明文意味着它能看到 Cookie、令牌与个人信息。中间人解密只应作用于自己有权调试的流量，采集到的会话应视为敏感数据处理，不要在共享环境长期留存。

## 小结

- 调试代理的核心价值是「在不改代码的前提下同时观察并干预两端流量」，规则层是它区别于纯抓包工具的关键。
- 七类能力中，观察是地基，匹配与改写分离是可扩展性的来源，模拟则是最容易误用的能力。
- 排障按「观察 → 缩小范围 → 构造反例 → 验证清理」推进，规则用完必须关掉。
- 顺序、作用域、时机是规则编排的三个隐含状态，遇到「规则没生效」优先查最终命中集合。
- 证书固定、私有协议、长期契约与生产流量治理都不属于调试代理的舒适区。
