# HTTPS、证书链与中间人

上一篇的结论是：纯 [CONNECT](/concepts/01-proxy) 透传时，代理看不进 HTTPS 的一个字节。本节回答「那[抓包](/concepts/05-capture)工具凭什么能看到明文」——先补齐 [TLS](/concepts/03-tls) 握手、[证书链](/concepts/03-tls)与信任锚的知识，再拆解 Whistle 把一条连接变成两段 TLS 的完整判定链。读完你能说清楚根证书为什么必须安装、哪些流量会被放行、以及这套能力的边界在哪里。 它承接 02 的 CONNECT 结论，把「看得见连接但看不见内容」推进到「看得见明文」，为 04 判断各协议能否改写打底。

给完全没读过源码的读者补三个基本词：TCP 只是可靠搬运字节的管道，HTTP 是写在这条管道上、按固定格式组织的明文文本；HTTPS 是把这段文本先加密再进管道，于是中间的代理默认只能看到密文，唯一能确定的是「客户端连向了哪个地址」。要让代理重新读到明文，前提是通信双方先确认彼此身份、再约定一把只有双方知道的密钥——这套准备工作正是本篇要拆的判定链，它的边界也由「谁被允许换证书」决定。

## 从握手到信任锚

TLS 握手要同时确认对方身份、并协商出只有双方知道的会话密钥。非对称加密负责认证与密钥交换，代价高；真正承载 HTTP 报文的是对称加密，因为加解密快、适合流式数据。所以握手的重点是安全地把对称密钥交到对方手里，而不是用 RSA 加密每一个字节。

### 证书链与信任锚

服务器发来的不是一张孤立证书，而是一条链：叶证书 → 中间 CA → 根 CA。浏览器逐层验签，直到遇到信任库里预置的根证书，这个根就是**信任锚**。根私钥长期离线，日常由中间 CA 签发，出问题时可单独吊销，不必惊动根。

证书里域名匹配靠 SAN（subjectAltName），而不是早期只填 CN 的写法；Whistle 签发叶证书时正是设置这个扩展（`lib/https/ca.js:241-242`）。[SNI](/concepts/03-tls) 则是客户端在第一个 ClientHello 里明文带上的目标域名，让同一 IP 上的多个站点能各自出示证书。[ALPN](/concepts/02-http)同样在握手里协商应用层协议，例如 `h2` 还是 `http/1.1`（`lib/https/h2.js:10` 的 `SUPPORTED_PROTOS = ['h2', 'http/1.1', 'http/1.0']`）。

把「域名匹配靠 SAN」再展开一句：早期只填 CN 的写法表达不了一个证书对应多个域名，SAN 用扩展字段列出所有可用域名，浏览器只认这张清单；Whistle 签发叶证书时正是设置这个扩展，否则客户端会因为「域名对不上」直接告警。

SNI 与 ALPN 都在第一个 ClientHello 里明文带出，代价是「访问了哪个域名」这件事本身并不加密——它们解决的是「同一 IP 上选哪张证书、选哪个协议」，而不是保密。

### pinning 与「装根证书」为何是前提

证书固定（pinning）指应用把预期证书或公钥写死在代码里，不理会系统信任库；mTLS 则反过来要求客户端也出示证书。两者都会让「换一张证书」立刻失败。而普通浏览器默认信任系统根 CA，这正是 HTTPS 抓包的唯一入口：把工具生成的根 CA 装进信任库，它签发的叶证书才被认作合法；不装，代理一解密客户端就会告警。

**为什么这样设计**：握手要同时确认身份、并协商出只有双方知道的会话密钥，所以把「慢但能验身份」的非对称加密用在认证与密钥交换上、把「快」的对称加密留给正文——否则用非对称加密逐字节搬运 HTTP 报文，开销会高到不可用。把「证书链」的结论展开成推理：服务器发来的不是一张孤立证书，而是一条叶证书 → 中间 CA → 根 CA 的链，浏览器逐层验签直到遇到信任库里预置的根，这个根就是信任锚；根私钥长期离线、日常由中间 CA 签发，出问题只吊销中间层，不必惊动根。

**代价与边界**：SAN 取代早期只填 CN 的写法来匹配域名，是因为 CN 表达不了多域名；SNI 在第一个 ClientHello 里明文带上目标域名，让同一 IP 上的多个站点能各自出示证书，代价是这个域名本身不加密。ALPN 在握手里顺带协商 `h2` 还是 `http/1.1`，把协议选择提前到建连阶段。

**pinning 与 mTLS 为什么是硬边界**：证书固定把预期证书或公钥写死在代码里、不理会系统信任库，mTLS 反过来要求客户端也出示证书；两者都会让「换一张证书」立刻失败。这也解释了「装根证书」为何是唯一入口：普通浏览器默认信任系统根 CA，只有把工具生成的根 CA 装进信任库，它签发的叶证书才被认作合法；不装，代理一解密客户端就告警。

**打个比方**：证书链像一层层背书的介绍信，根 CA 是人人认得的公证处；pinning 则像对方只认一枚特定指纹、连公证处的话都不听，自然没法换人。

**自己验证**：顺着「装根证书」这条线索问自己：如果某应用不读系统信任库、而是自己写死了公钥，把根 CA 装进系统还有用吗？答「没有」，就等于亲手验证了 pinning 为什么会被列入放行黑名单。

这一段补的是「信任从哪来」；下一段才回答「拿到信任之后，代理怎么把一条连接拆成两段」。

## 两段 TLS 的 MITM 模型

中间人不是「破解 TLS」，而是**让客户端和代理、代理和源站各做一次独立握手**。左侧客户端以为在和 `example.com` 说话，对面其实是 Whistle 用本地 CA 现签的叶证书；右侧 Whistle 以普通客户端身份与源站握手。两段之间的代理拿到明文，规则改写、抓包、重放由此可能。

对照纯 CONNECT 透传：透传只有一条 TCP 管道、零解密零改写；MITM 是两条加密连接加一段明文桥，代价是必须持有客户端信任的签发权，且每多一段握手就多一份延迟与失败面。

**为什么这样设计**：中间人不是「破解」加密，而是让客户端与代理、代理与源站各做一次独立握手——左侧客户端以为在和 `example.com` 说话，对面其实是 Whistle 用本地 CA 现签的叶证书；右侧 Whistle 以普通客户端身份与源站握手。两段之间的代理拿到明文，规则改写、抓包、重放才由此可能。把「与纯透传对照」的结论展开成推理：透传只有一条 TCP 管道、零解密零改写，MITM 是两条加密连接加一段明文桥；多出来的这一段明文，正是所有调试能力的来源，也是所有风险的来源。

**代价与边界**：代价清晰——必须持有客户端信任的签发权，且每多一段握手就多一份延迟与失败面；边界是遇到 pinning 或 mTLS 时这套模型直接失效，只能退回纯透传。换句话说，MITM 与透传不是「高级 / 低级」，而是两种能力档位，按流量能不能换证书来选。

**打个比方**：像邮局在中间拆开信封、抄一份内容再重新封好寄出；收件人之所以不察觉，是因为信封上的封蜡盖的是他信任的那枚章。一旦对方只认特定封蜡，这套手法就穿帮。

**自己验证**：对照那张两段 TLS 的示意图，用手指沿左、右两条箭头各走一遍，确认「两次握手」与「中间一段明文」是同时存在的；能指出明文桥在哪，就理解了后面所有解密判定到底在争什么。

## Whistle 何时决定解密

解密很贵也有风险，所以默认不是「所有 CONNECT 都拆」。总闸门是 `lib/tunnel.js:168-213` 的 `isIntercept()`，它把几类信号组合起来：

- **策略头**：`lib/tunnel.js:144-148` 读取 `x-whistle-policy`（`lib/config.js:67`），`tunnel` / `connect` 要求纯透传，`weakTunnel` 只在显式要求时解密；`intercept` / `capture` 则强制解密（`lib/tunnel.js:179-187`）。
- **规则与开关**：`filter.https` / `filter.capture` / `filter.intercept` 以及 `disable.https` / `disable.capture` 决定这一条是否豁免（`lib/tunnel.js:168-177`）。
- **全局抓包开关**：`lib/tunnel.js:195` 检查 `properties.isEnableCapture()`，未开启时不主动解密。
- **系统流量黑名单**：即使开启抓包，`lib/tunnel.js:199-200` 也会放行 Cronet UA 与 Apple、Microsoft 等系统域名（`lib/tunnel.js:26-27` 的 `CRONET_RE` / `SYS_HOST_RE`），避免破坏系统服务与证书固定流量。
- **自定义证书**：`lib/tunnel.js:190-197`、`lib/tunnel.js:207-212` 在存在自定义证书或配置了 Proxifier 时仍可能放行解密。

为什么黑名单这么保守？这些客户端大量使用 pinning，换证书会整片失败，宁可看不到也不能让设备断网。

**为什么这样设计**：解密既贵又有风险，所以默认不是「所有 CONNECT 都拆」——总闸门把策略头、规则与开关、全局抓包开关、系统流量黑名单、自定义证书几类信号组合起来，任一信号都能否决解密。把结论展开成推理：像 `tunnel` / `connect` 这类策略头明确要求纯透传，黑名单里的系统域名又大量使用 pinning，换证书会整片失败，因此「宁可看不到也不能让设备断网」成了默认倾向。

**代价与边界**：保守的代价是你明明开了抓包、却仍有些条目看不到明文，容易误判成「没抓到」；边界是这套判定只决定「要不要拆」，拆不拆得开还要看下一节的首包识别与证书签发。

**打个比方**：`isIntercept()` 像机场安检的分流口，先看旅客有没有豁免证件（策略头）、再看是否属于免检名单（系统域名），最后才决定要不要开箱；多数旅客走免检通道，是为了不让整条队伍停摆。

**自己验证**：排查「某条 HTTPS 没被解密」时，按顺序核对三类信号——策略头是否要求纯透传、全局抓包开关是否打开、目标是否落在系统域名黑名单里；这个顺序正是判定链的组合顺序，比直接改规则更快定位。

## 首包识别、SNI 与证书签发

决定解密后，代理还不知道隧道里跑的是 TLS、明文 HTTP 还是 h2c。`lib/https/index.js:1184-1234` 用 `util.readOneChunk` 读第一个数据包再分流：`HTTP_RE` 命中说明是明文 HTTP（`lib/https/index.js:1117`），由 `:1215-1226` 把它作为 `connection` 事件塞回 HTTP 解析器；`HTTP2_RE` 命中说明是 h2c preface（`lib/https/index.js:1118`）。其余情况在 `:1232` 用的是**反向判定** `if (!isHttpH2 && chunk[0] != 22) return next(chunk);`：首字节不是 22 且不是 h2c preface 就回退透传，换言之只有 TLS 握手记录（首字节 22，handshake 类型）或 h2c preface 才继续往下解密。

```js
// lib/https/index.js:1231-1234
var isHttpH2 = HTTP2_RE.test(headersStr);
if (!isHttpH2 && chunk[0] != 22) {
  return next(chunk);
}
```

确认是 TLS 后，`lib/https/index.js:1295` 调用 `checkSNI(chunk)`（`lib/https/index.js:9` 引入 `sni` 包）从 ClientHello 里取出域名，据此签发对应叶证书。根 CA 在启动时就绪：`lib/https/ca.js:427-441` 的 `createRootCA()` 先读取本地已有的根密钥与根证书，读不到则由 `lib/https/ca.js:471-473` 的 `resetRootCA()` 新建，调用点在 `lib/https/ca.js:580`。

有效期分两档，不可混为一谈：`lib/https/ca.js:46-49` 定义 `MIN_DATE = ONE_DAY * 7`、`MAX_DATE = ONE_DAY * 36`，`:558-573` 的 `createCert` 在 `isShortPeriod` 分支给**叶证书**设 `notBefore = now - 7 天`、`notAfter = now + 36 天`——提前 7 天生效是为容忍客户端时钟回拨，36 天上限则顺应 Apple / Chromium 对证书寿命的限制（`:563-564` 的注释）。`createSelfCert`（`:213-217`）正是传 `true` 走这一档；根证书由 `createCACert`（`:479`）不传该参数，落到 else 分支 `notAfter = now + ONE_YEAR * 10`，即约十年。

另有一条兼容路径：`lib/https/index.js:1324` 在 `enable://emudhra` 生效时置 `enableEmudhra`，`lib/https/ca.js:224,264` 改用 `emudhra.subject` 作签发者、由 `emudhra.sign` 签名；`lib/https/emudhra.js:6` 注明这套密钥与链来自 mitmproxy 公开披露的提交，只用于兼容特定 Android 客户端，**不是可信根证书，也不应视作安全实践**，详见[《TLS 概念精解》](/concepts/03-tls)。

握手完成后，`lib/https/index.js:1102-1111` 的 `handlers.request` 用 `server.emit('request', req, res)` 把明文请求塞回 Express 中间件链：HTTPS 与明文 HTTP 最终共用同一套规则与改写逻辑，前面所有复杂性只为还原出 `req` / `res`。

这里其实是**两个互不影响的信任边界**：入站一侧，客户端是否信任代理伪造的叶证书，只取决于本地根 CA 有没有装进系统信任库（上一节「装根证书」）；出站一侧，`lib/config.js:65` 默认 `config.rejectUnauthorized = false`，代理作为普通客户端连源站时不校验对方证书，以便处理自签名环境，只有 `--mode safe`（或 `rejectUnauthorized`）才在 `lib/config.js:809-810` 打开校验。装好根 CA 并不会顺带让出站校验变严，`--mode safe` 打开的也只是出站这一段；两段各管各的信任，互不传递。这是便利与安全的取舍。

**为什么这样设计**：决定解密后，代理还不知道隧道里跑的是加密握手、明文 HTTP 还是 h2c，于是先读第一个数据包再分流——这是「先看一眼再决定往哪送」的最小代价做法。把那段反向判定展开成推理：`if (!isHttpH2 && chunk[0] != 22) return next(chunk)` 的意思是，首字节不是 22（握手记录类型）且不是 h2c preface 就回退透传；换言之只有加密握手记录或 h2c preface 才继续往下解密，其余一律当普通字节放走。

**代价与边界**：代价是首包必须被缓冲一小段才能判定，且判定依赖首字节这种「约定」而非强校验；边界是它只识别「像不像握手」，真正能不能签出证书还要看 SNI 能否取出域名、以及本地根 CA 是否就绪。另要记住两个互不影响的信任边界：入站一侧客户端信不信任伪造叶证书，只取决于本地根 CA 装没装进信任库；出站一侧默认不校验源站证书，只有 `--mode safe` 才打开校验。装好根 CA 并不会顺带让出站校验变严，两段各管各的信任。

**打个比方**：首包识别像分拣员先看一眼外包装上的标签再决定投哪条传送带，而不是拆开包裹逐件清点；SNI 则像标签上写着的收件城市，据此现签一张对应门牌的临时通行证。

**自己验证**：把 `--mode safe` 打开再关掉，对比出站侧是否校验源站证书，就能亲自确认「装根证书不会让出站校验变严」这条边界；再对照叶证书 7 天提前生效 / 36 天有效、根证书约十年这两档，问自己为什么短周期只给叶证书——答案正是「容忍客户端时钟回拨 + 顺应浏览器对寿命的限制」。

握手完成后明文请求被塞回 Express 中间件链，HTTPS 与明文 HTTP 最终共用同一套规则与改写逻辑：前面所有复杂性，只为还原出一对 `req` / `res`。

## 合规与风险

- **私钥本地生成与保存**：根密钥在本机生成并存于数据目录的 `certs` 下（`lib/https/ca.js:19`、`lib/https/ca.js:27-30`、`lib/https/ca.js:427-441`），不会上传。一旦泄露，持有者就能为任意域名签发被你信任的证书，切勿备份到网盘或共享仓库。
- **根证书信任范围**：安装根 CA 意味着该系统上**所有应用**的 TLS 都可能被这台机器上的 Whistle 解密，不只是浏览器里的调试页面。用完及时取消信任，尤其在共用开发机上。
- **不要在生产或他人设备上滥用**：仅在自己可控的开发、测试环境，且对相关流量有明确授权时启用；未经同意解密他人通信既不合规也可能触犯法律。
- **pinning 与 mTLS 场景**：遇到证书固定或双向认证，换证书会直接导致握手失败，应改用纯透传、让客户端直连，或由业务方提供专用调试构建，而不是强行绕过。

**为什么这样设计**：把私钥本地生成与保存、根证书信任范围、合规边界列成清单，是因为这套能力的风险不在算法、而在「谁被授予了签发权」。把第一条展开成推理：根密钥在本机生成、存于数据目录的 `certs` 下、不会上传，一旦泄露，持有者就能为任意域名签发被你信任的证书——因此它不能备份到网盘或共享仓库。

**代价与边界**：安装根 CA 意味着该系统上所有应用的加密流量都可能被这台机器上的 Whistle 解密，不只是浏览器里的调试页面；用完及时取消信任，尤其在共用开发机上。边界也很明确：仅在自己可控、且对相关流量有明确授权的开发测试环境启用，遇到 pinning 与 mTLS 应改用纯透传或由业务方提供专用调试构建，而不是强行绕过。

**打个比方**：装根 CA 像把一把能开全楼房门的万能钥匙交出去，方便了自己巡检，也意味着必须把它随身收好、用完即还。

**自己验证**：装好根 CA 后，随便打开一个非调试用的应用看它是否也能连上，就能亲身体会「信任范围是整台系统、不是单个页面」；这一步比记住条文更能说明为什么用完要取消信任。

## 常见误解

1. **容易以为 MITM 是「破解了加密」，其实它只是让客户端与代理、代理与源站各做一次独立握手**：代理能拿到明文，靠的是持有客户端信任的签发权，而不是攻破了算法；代价是每多一段握手就多一份延迟与失败面。
2. **容易以为装好根证书就万事大吉，其实入站与出站是两个互不影响的信任边界**：客户端信任伪造叶证书只取决于本地根 CA 是否装进信任库；出站侧默认 `config.rejectUnauthorized = false`，只有 `--mode safe` 才打开校验，装根 CA 并不会顺带让出站校验变严，对照见[《易混淆概念辨析》](/concepts/08-confusions)。
3. **容易以为开启抓包就会解密所有 CONNECT，其实判定会因策略头、规则、全局开关、系统域名黑名单与自定义证书放行一大批流量**：这些客户端大量使用 pinning，换证书会整片失败，宁可看不到也不能让设备断网。
4. **容易以为叶证书和根证书有效期是一套规则，其实二者分两档**：叶证书 7 天提前生效 / 36 天有效以顺应浏览器对寿命的限制，根证书约十年，两者不可混为一谈。

## 小结

- 非对称加密负责认证与密钥交换，对称加密承载正文；信任锚是系统预置根 CA。
- SAN 匹配域名、SNI 指示目标站点、ALPN 协商协议，pinning 与 mTLS 会拒绝替换证书。
- MITM 用两段独立 TLS 换出中间明文，与纯透传是两种能力档位。
- `isIntercept()` 综合策略头、规则、全局开关、系统黑名单与自定义证书决定是否解密。
- 首包以「非 22 且非 h2c preface 就透传」反向分流，SNI 驱动本地 CA 签发短周期叶证书（7 天提前生效 / 36 天有效，根证书约十年），明文回流 Express。
- 本篇为 [《HTTP/2、WebSocket 与流量形态》](/domain/web-protocols) 准备了「明文已到手」这个前提：只有先拆出明文，04 才谈得上区分排队、多路复用与帧，并判断各协议能改写多少。
