# 一张图看懂全局架构

前三篇分别解释了代理形态、TLS 中间人和协议流量，这些模型在代码里并不是三个独立系统，而是同一条主干上的不同切面；紧接其后的 [《抓包调试的能力模型》](/domain/debugging-workflow) 把代理该提供哪些能力收拢成一张清单，却留下了本篇要回答的问题：这些能力究竟落在进程的哪些模块里、图上的一个方框对应哪个文件。本节用一张图把「四类入口 → 中间件链 → 规则/改写/抓包 → 出站 → 事件总线 → 进程与存储」串起来，并给出精确到文件与行号的坐标，把那张能力清单逐项落回代码主干。读完你应当能拿着这张图，独立定位任何一次请求经过的模块，说清「为什么这样分层」以及「代价与边界」在哪里。

## 一张图上的主干

图的左侧是**四类入口**：`request`（普通 HTTP 与解密后的 HTTPS）、`connect`（CONNECT 隧道）、`upgrade`（WebSocket）、`clientError`（畸形报文），全部挂在同一个 [`http.Server`](/concepts/04-runtime) 上（`lib/index.js:36-61`）。为什么坚持单端口多事件？因为对客户端来说只有一个代理地址，配置 PAC 或系统代理时不必区分协议类型。

中部是**中间件链**：所有入口最终都被归一化成 Express 的 `req` / `res`，依次经过初始化、Web 界面路由、规则匹配、请求改写、数据采集、响应改写，最后交给 handlers 出站。右侧是**规则/改写/[抓包](/concepts/05-capture)**这组横切能力，它们不自己收发请求，而是通过事件总线订阅链路上的数据。最外层则是**进程与存储**：后台服务、[插件](/concepts/07-extension)、weinre 跑在独立子进程里，规则、值、属性与证书落在本地数据目录。

一句话概括这张图：Whistle 把「协议差异」消化在入口层，把「业务差异」消化在中间件链，把「可观测性」外挂到事件总线。三层解耦之后，新增一种协议通常只需补一个入口，新增一种调试能力通常只需挂一个监听器。

**为什么这样分层**：把那句概括拆成推理——入口层专门消化「协议差异」，是因为普通请求、CONNECT、WebSocket 与畸形报文进门时的报文形态完全不同，若不在最前面各自归一化，后面每个环节都得先回答「我手里是哪种流量」；中间件链消化「业务差异」，是因为规则匹配、改写、抓包都只愿意面对一种统一的 `req` / `res`，顺序固定后每道工序只做一件事；可观测性外挂到事件总线，是因为抓包数据既要给 Web UI、也要给插件和日志，让链路把数据广播出去，比让每个环节各自回调所有消费方更松耦合。三层各管一类差异，正是「新增一种协议只需补一个入口、新增一种调试能力只需挂一个监听器」的前提。

**代价与边界**：分层的代价是一次请求要穿过一长串 `app.use`，任何一段出错或被插队，都会改变后续阶段看到的内容，排障时必须按链序逐段排除。边界也更具体：「补一个入口」要求新入口能把自己归一化成 Express 的 `req` / `res`，否则仍得动中间件链；「挂一个监听器」只适用于只读的调试能力，一旦要干预请求内容，就必须回到链里排队，而不能停在外层。

**为什么坚持单端口多事件**：原文那句「对客户端来说只有一个代理地址」可以再推一步——PAC 与系统代理只能填一个主机和端口，若普通 HTTP、CONNECT、WebSocket 各占一个端口，客户端就得为不同协议分别配置，移动端与桌面应用根本无法统一接入；把四类事件挂到同一个 `http.Server`，等于把「选哪个端口」这个问题从客户端彻底移除。代价是服务端必须自己从报文形态判别来的是哪一种事件，`connect` 因此要先判明流量该交给哪条路径，`clientError` 得单独兜住畸形报文，任何一类判别失误都会被当成另一类来处理。边界是它只统一了「进门」这一步，进门之后四类流量仍走各自的子系统，并不是真的一套逻辑通吃。

**打个比方**：这张图像一座机场——四类入口是不同的安检通道，进去之后都汇到同一条行李传送带（中间件链），传送带旁的分拣员各管一道工序；监控系统并不碰行李，只从旁边的传感器取信号（事件总线）。想加一条新通道，只要它把行李摆成传送带认得的姿势即可，不必重排整条线。

**一次请求在这张图上的输入 → 动作 → 输出**：输入是客户端发到唯一代理地址的一段字节（普通请求、CONNECT、WebSocket 升级或畸形报文）；动作是入口层先判明形态并归一化成 Express 的 `req` / `res`，中间件链依次定规则、改请求、采数据、改响应，出站 handler 再把它发往源站；输出则是回写给客户端的响应，以及沿途被广播到事件总线的结构化抓包数据。把这三段对上号，就能解释一个常见现象：抓包列表里出现某条请求，不等于它已经被成功转发——广播发生在链路中途，出站是更靠后的另一道工序。

**为什么「方框」值得逐个对应到文件**：领域基础四篇给的是模型（代理有几种形态、TLS 怎么拆、帧长什么样、调试要哪些能力），模型说的是「应当如此」，代码记的是「实际如此」。B 组这几篇正是把「应当」落到「实际」的转折：图上每画一个方框，都要回答它由哪个文件承载、和相邻方框交换什么、以及不这么做会坏在哪里。只读模型容易停留在「大概是这样」，只有把方框钉到文件上，才能在排障时顺着链接一路点进去。

**代价与边界（再补一层）**：把模型钉到文件上也有代价——源码坐标会随版本变动，而模型不会；本篇给出的行号只用于「此刻在这份代码里能找到它」，真正稳定的是「入口 / 链 / 横切 / 进程」这四层职责的划分。因此读源码时若发现锚点移位，不必怀疑图错了，先按职责判断它该落在四层里的哪一层，再用文件名去定位即可。边界是这张图刻意省略了规则如何匹配、证书如何签发、帧如何缓存这些细节，它们各自有专篇，图上只保留「谁和谁相邻」的关系。

**自己验证**：对照本篇「读源码时该从哪个文件切入」表，只打开 `lib/index.js` 一个文件，就能同时找到 `server.on(...)` 与 `middlewares` 两个锚点；这正好证明「四类入口」与「中间件链」写在同一个文件、却分属图的左右两侧——入口消化协议、链消化业务不是两张图，而是同一段代码的两个视角。

## 中间件链的精确顺序

顺序写在 `lib/index.js:40-52`，是理解全站最关键的一段代码：

```js
// lib/index.js:39-52
var proxyEvents = new EventEmitter();
var middlewares = ['./init', '../biz']
  .concat(require('./inspectors'))
  .concat(config.middlewares)
  .concat(require('./handlers'));
server.timeout = config.timeout;
server.requestTimeout = 0;
// ...
middlewares.forEach(function (mw) {
  mw && app.use((typeof mw == 'string' ? require(mw) : mw).bind(proxyEvents));
});
```

展开后依次是：`lib/init.js` → `biz/index.js` → [inspectors](/concepts/05-capture)（`rules` → `req` → `data` → `res`，见 `lib/inspectors/index.js:1-8`）→ `config.middlewares`（用户自定义）→ handlers（`file-proxy` → `http-proxy` → `error-handler`，见 `lib/handlers/index.js:1-7`）。每一个都用 `app.use(mw.bind(proxyEvents))` 注册，也就是说**所有中间件的 `this` 都指向同一个事件总线**。

为什么是这个顺序？`lib/init.js` 必须先给 `req` / `res` 挂上 Transform 能力（`lib/init.js:87-155`），后面的改写才有支点；`biz/index.js` 要抢在规则之前识别 Web UI 与插件界面请求，避免管理流量被用户规则误伤；inspectors 按「先定规则、再改请求、再采数据、最后改响应」推进，符合一次请求的生命周期；handlers 放在末尾，因为它是真正的出站动作，`error-handler` 兜底所有未被处理的异常。

各阶段的分工也值得记住：`lib/inspectors/rules.js` 负责解析并应用规则与编解码，中间两阶段处理请求与响应的具体内容，`lib/inspectors/data.js` 负责抓包缓冲；出站的 `lib/handlers/http-proxy.js` 发起到源站的请求，`lib/handlers/file-proxy.js` 处理本地文件与协议映射。

**为什么是这个顺序**：把结论展开成推理——`lib/init.js` 先挂 Transform 能力，是因为后面的请求改写、响应改写都要在 `req` / `res` 这两个流上插入变换，没有这层包装就没有「改写」的支点；`biz/index.js` 抢在规则之前，是为了先认出 Web UI 与插件界面的管理流量，否则用户写的一条通配规则可能把管理界面自己也改写掉；inspectors 按「先定规则、再改请求、再采数据、最后改响应」推进，是因为一次请求的生命周期本就是这个次序，先有 [规则 DSL](/concepts/06-rules) 才知道要不要改写、先采到原始数据才谈得上改响应；handlers 放末尾，因为它是真正的出站动作，`error-handler` 必须兜在所有阶段之后才能接住任何一处抛出的异常。

**代价与边界**：固定链序换来的可预测性，代价是「顺序即语义」——把 `config.middlewares` 或某个 inspector 挪一位，规则可能还没生效就被读到、抓包可能采到改写前或改写后的不同内容，而这类问题不会报错、只会表现为「结果与预期不符」。边界是这条链只描述「一次请求期内」的加工，启动期的装配、后台任务、插件子进程都不在链上；把两者混为一谈，正是后面要澄清的 `lib/init.js` 命名陷阱。

**为什么所有中间件都 `bind(proxyEvents)`**：`app.use(mw.bind(proxyEvents))` 让分散在各文件的模块共享同一个 `this`，于是谁都可以借它抛事件、收事件，而不必互相 `require` 形成网状依赖。代价是 `this` 被占用后不能再指向模块自身，模块间若想直调就得另走 `exportInterfaces` 暴露的接口；这也是事件总线既是「解耦工具」又是「唯一通信约定」的原因。

**把链序当成一条流水线看**：`lib/init.js` 的输入是刚进门的原始 `req` / `res`，输出是挂好 Transform 与错误兜底的可改写流；`biz/index.js` 的输入是这个流，输出是「已判定是不是管理流量」的同一个流；inspectors 四阶段的输入依次是「原始请求 → 带规则的请求 → 改写后的请求 → 待回写的响应」，输出是「已匹配规则、已改写、已采集、已定型」的结果；handlers 的输入是这份结果，输出是发往源站的请求与最终响应。可见链上每一段都不重新收包，只是在同一个 `req` / `res` 上叠加信息——这正是「归一化成一种表示」换来的好处：任何一段都能假设上游已经把该补的补齐了。

**另一处代价与边界**：也因为大家共用同一对 `req` / `res`，一段若把请求信息改得不符合下游预期，错误不会当场暴露，而是等到规则匹配或出站才显现；所以「顺序即语义」不只是排序问题，更是「谁有权在什么时候改什么」的约定。自定义 `config.middlewares` 被放在 inspectors 之后、handlers 之前，正是让用户既能看到规则结果、又还来得及在出站前干预。

**自己验证**：顺着上面那段装配代码数一数 `middlewares` 数组由几段 `concat` 拼成、`forEach` 里又把每一项 `bind` 到谁；再对照「读源码时该从哪个文件切入」表里「请求被谁加工」一行的 `middlewares` 锚点，就能确认链序不是文档归纳，而是数组拼接的字面顺序。

## 事件总线与抓包数据

`lib/index.js:39` 的 `proxyEvents = new EventEmitter()` 是内核总线。它有两个作用：一是作为 `this` 注入每个中间件，让分散的模块能互相发事件而不必互相 require；二是通过 `lib/index.js:215-241` 的 `exportInterfaces` 对外暴露 `rules`、`util`、`rulesUtil`、`httpsUtil`、`pluginMgr`、`logger`、`socketMgr`、`setAuth`、`setShadowRules` 等接口，插件与 Web 界面由此获得内核能力。

抓包就是这套机制的典型用法。链路各处把结构化数据 `proxy.emit('request', ...)`（`lib/tunnel.js:124,343`、`lib/https/index.js:254`）或 `proxy.emit('frame', ...)`（`lib/socket-mgr.js:44,118`）抛到总线上，`lib/util/data-server.js:87-95` 的 `enable()` 只做一件事：监听 `request` 与 `frame`，写入缓存并定时清理。为什么不让 inspectors 直接写界面？因为抓包数据既要给 Web UI，也要给插件和日志，事件广播比逐处回调更松耦合。

界面取数据用的是短轮询而非 WebSocket：`biz/webui/htdocs/src/js/data-center.js:88,446` 把地址拼成 `cgi-bin/get-data`，`biz/webui/htdocs/src/js/data-center.js:1157-1159` 依据 `hasNew` 决定下一次是 100 ms 还是 900 ms 再拉。有新数据就加快、空闲就放慢，这是在实时性与请求量之间取的折中。

**为什么用事件广播而不是直接回调**：这套机制的载体是 [EventEmitter](/concepts/04-runtime)，它让链路各处只管 `proxy.emit('request', ...)`、`proxy.emit('frame', ...)` 把结构化数据抛出去，谁关心谁自己监听。把「抓包既要给 Web UI、也要给插件和日志」这句展开：若让 inspectors 直接写界面，就得在链路里硬编码三个消费方，日后每多一个消费方都要改链路；改成广播后，`lib/util/data-server.js` 只需监听 `request` 与 `frame`、写入缓存并定时清理，新增消费方等于新增一个监听器。代价是事件「发出即忘」，链路拿不到消费方的处理结果，也不保证消费方一定在线，所以抓包只能做旁路观测，不能用来决定请求怎么转发。

**代价与边界**：事件总线把模块解耦得很干净，但也让调用关系从「看得见的 require」变成「看不见的事件名」，排障时要靠 `exportInterfaces` 暴露的接口清单反查谁在收、谁在发。它的边界是「同进程」——子进程、前端界面收不到这些事件，前者要靠另一套跨进程交接，后者要靠下面说的 HTTP 轮询，这正解释了为什么变更通知不能只靠这一条总线。

**短轮询为什么是 100 / 900 ms 两档**：界面把地址拼成 `cgi-bin/get-data`，依据 `hasNew` 决定下一次 100 ms 还是 900 ms 再拉——有新数据就加快、空闲就放慢。这是在「实时性」与「请求量」之间取的折中：一味用 100 ms 会在空闲时空转大量请求，一味用 900 ms 又会让刚产生的抓包数据迟迟不显示。代价是界面永远有最多一档间隔的延迟，做不到服务端推送那种实时；好处是只需一个定时轮询、不依赖长连接，在代理本身就可能改写连接的场景里更稳。

**`exportInterfaces` 为什么单独存在**：总线本身只是 `proxyEvents` 这个内部对象，插件与 Web 界面若直接持有它，就能随意触发内部事件、绕过约束；`exportInterfaces` 把它包装成一份白名单式的接口清单（`rules`、`util`、`rulesUtil`、`httpsUtil`、`pluginMgr`、`logger`、`socketMgr` 等），既让外部拿得到能力，又把「能用什么」框在可控范围内。代价是内核每加一项能力都要显式登记进这份清单，否则插件看不见；边界是它只做「暴露」，不做「隔离运行」——插件代码跑不稳仍要靠子进程那一层来兜，两条线不能互相替代。

**打个比方**：事件总线像车间里的广播喇叭，各工位把「做完了什么」喊一声就继续干活，质检台、看板、记录员各自记各自的，谁也不必认识谁；代价是喇叭只负责喊，收没收到、记没记全，喊的人并不知道。

**抓包数据的输入 → 动作 → 输出**：输入是链路各处在关键节点抛出的 `proxy.emit('request', ...)` 与 `proxy.emit('frame', ...)`；动作是 `lib/util/data-server.js` 的 `enable()` 监听这两个事件、把结构化数据写入缓存并定时清理；输出是 `cgi-bin/get-data` 每次轮询返回给界面的增量，界面再依据 `hasNew` 决定下一档间隔。三段分开看，就能明白「抓包」既不是入口层的一个分支、也不是出站层的一步，而是挂在链路旁的一条只读观测：它不影响请求怎么转发，只决定我们事后能看到多少。

**缓存的代价与边界**：只读观测之所以便宜，来自「有缓存、会定时清理」——缓存保证界面随时拉得到，定时清理保证长时间挂着不会把内存吃满；代价是历史数据并不永久保留，清掉之后无法从总线上补回。边界是它只覆盖「链路主动抛出的事件」，任何没被抛出的中间状态都不在抓包里，排查时不能把「列表里没有」直接当成「没有发生过」。

**自己验证**：在抓包界面开着的时候留意 `cgi-bin/get-data` 的两次间隔——刚触发一条请求时刷新明显变快、静置一会儿又变慢，就能直观看出「有新数据加快、空闲放慢」这两档，而不需要任何额外工具。

## 进程三层与存储

[进程模型](/concepts/04-runtime)分三层，理解它能避免把「启动」和「运行」混为一谈：

1. **CLI 进程**：`w2 start` 等命令由 `bin/whistle.js:3` 引入的 `starting` 托管，负责参数解析、状态查询与把业务进程转入后台。
2. **detached 业务进程**：真正运行 `index.js:1` / `lib/index.js:36` 的常驻进程，监听主端口；CLI 退出后它仍在。
3. **[pfork](/concepts/07-extension) 子进程**：后台服务、每个插件、weinre 各自独立，分别见 `lib/service/index.js:1,10`、`lib/plugins/index.js:2`、`biz/weinre/index.js:1`。为什么要隔离？插件是第三方代码，崩溃或内存泄漏不该带走代理主进程。

`--cluster` 是另一条正交的线：只有显式传入时，`index.js:200-211` 才用 `cluster.fork` 起多个 worker 分担端口（`bin/whistle.js:178` 定义该选项）。它解决的是多核利用，与 pfork 的「功能隔离」不是一回事，默认并不启用。

存储统一落在 `~/.WhistleAppData/.whistle/`：`lib/util/common.js:598-603` 给出默认根目录 `~/.WhistleAppData`，`lib/config.js:1068-1069` 拼上 `dataDirname`（`package.json:5` 中为 `.whistle`）。其下 `rules`、`values`、`properties` 由 `lib/config.js:148-150` 定义，`certs` 由 `lib/https/ca.js:19` 创建并存放根 CA 与叶证书。规则、值、属性、证书分别对应「配置」「素材」「开关」「信任」，拆开存放也便于备份与迁移。

**为什么分三层**：把「避免把启动和运行混为一谈」展开——CLI 进程解析参数、发起守护化、打印提示后即退出，是短命的；detached 业务进程持有主端口、常驻运行中间件链，是长命的；pfork 子进程承载后台服务、插件与 weinre，是随时可生可灭的。三层把「谁负责拉起服务」「谁负责接流量」「谁负责跑第三方代码」拆开，于是插件崩溃或内存泄漏只能带走它自己那个子进程，不会波及代理主进程；Web UI 停止响应也不等于端口不再监听。代价是三层之间必须显式通信，排障时先要判断问题出在哪一层，不能只看一个进程的状态。

**为什么 `--cluster` 与 pfork 是两条正交的线**：前者用多个 worker 分担同一个主端口，解决的是多核利用；后者按功能把第三方代码隔开，解决的是稳定性隔离。两者可以同时存在、互不替代，也默认都不启用——`--cluster` 只在显式传入时才 `cluster.fork`，pfork 则只在真正需要加载某个插件或后台服务时才拉起。把两者混成「都是多进程」，就会误以为默认起了一堆 worker，或误以为 pfork 能提升吞吐量。边界是：worker 共享端口但不共享数据目录，pfork 子进程不碰主端口。

**存储为什么拆成四类**：`rules` / `values` / `properties` / `certs` 分别对应「配置」「素材」「开关」「信任」。`certs` 单独放根 CA 与叶证书，是因为信任材料与普通配置的生命周期不同、且最需要小心备份；四类拆开后，迁移一个实例只需搬对应目录，不必把规则和证书一起覆盖。代价是配置散落多处，同一个行为既要看启动参数、又要回到落盘目录里找对应子目录，排障时不能只盯一处。

**为什么默认目录要拆成两段拼接**：把「默认根目录」和「数据目录名」分开（`~/.WhistleAppData` 与 `dataDirname`），是为了让「用户级根目录」与「本项目实例名」各自可替换——换一个用户名不必改项目代码，换一个目录名也能在同一台机器上并存多套数据。代价是排障时要先分清问题出在根路径还是子目录；边界是这里只决定「落在哪」，不决定「合并优先级」，后者要等后面的配置系统篇才讲得清。

**三层进程的输入 → 动作 → 输出**：CLI 进程的输入是用户敲下的命令与参数，输出是一个被拉起、且与终端解耦的业务进程以及一份运行记录；业务进程的输入是这份参数与主端口上的流量，输出是转发出去的请求、回写的响应与落到本地目录的数据；pfork 子进程的输入是主进程交付的功能任务，输出是各自独立的结果或消息。三层次第交接，正好把「启动」和「运行」分成两件事：CLI 退出不等于服务停止，子进程重启也不等于主端口重新监听。

**隔离的代价与边界**：按功能隔离的代价，是插件与内核之间不能再直接共享内存对象，一切交互都得经过跨进程的交接，开发与排障都比单进程麻烦；边界是这种隔离只防「崩溃与泄漏」，并不防「插件写坏规则」——规则仍在主进程的链上生效，隔离的是代码运行环境，不是配置影响力。

**自己验证**：执行 `w2 start` 把服务拉起来，再到 `~/.WhistleAppData/.whistle/` 下数一数 `rules` / `values` / `properties` / `certs` 是不是各自独立成目录；能数清这四类数据分开落盘，就理解了「配置 / 素材 / 开关 / 信任」为什么要拆开，也就能顺着「读源码时该从哪个文件切入」表的锚点，在 `lib/config.js` 与 `lib/https/ca.js` 里分别找到它们的定义处。

## 读源码时该从哪个文件切入

带着问题找入口，比按目录顺序翻要快得多：

::: cols 22|28|28|22
| 想弄清什么 | 切入文件 | 关键锚点 | 顺延到 |
|---|---|---|---|
| 服务怎么起来 | `index.js` | `cluster.fork` | `lib/config.js` |
| 四类入口在哪 | `lib/index.js` | `server.on(...)` | `lib/tunnel.js` |
| 请求被谁加工 | `lib/index.js` | `middlewares` | `lib/inspectors/` |
| 规则如何生效 | `lib/inspectors/rules.js` | `getDecoder` | `lib/rules/` |
| 出站怎么发 | `lib/handlers/http-proxy.js` | `req.request` | `lib/util/` |
| 抓包数据在哪 | `lib/util/data-server.js` | `proxy.on('request')` | `data-center.js` |
| HTTPS 怎么拆 | `lib/https/index.js` | `readOneChunk` | `lib/https/ca.js` |
:::

这张表本身就是「图上的方框对应哪个文件」的索引：想弄清「服务怎么起来」就从 `index.js` 的 `cluster.fork` 切进去，想弄清「四类入口在哪」就找 `lib/index.js` 的 `server.on(...)`，想弄清「请求被谁加工」还是回到 `lib/index.js` 的 `middlewares`。注意同一个 `lib/index.js` 在表里出现两次——正对应本篇反复强调的那点：入口装配与中间件链是同一段代码的两个视角，不是两个子系统。

**为什么这样设计 / 代价与边界**：按「问题 → 锚点」组织，而不是按目录树组织，是因为读者脑子里装的是「一次请求会经过什么」，而源码是按「模块职责」摆放的，两者顺序不同；表格把这两种顺序对齐了一次。代价是它只列了八个最常用锚点，覆盖不了所有分支，遇到表里没有的问题仍得回到图上判断该往左（入口）、往中（链）还是往右（横切能力）找。边界是锚点是字符串而非行号语义——同一份源码改版后字符串可能移位，但「哪个文件管哪类事」的分工不变。

**自己验证**：任选表里一行，比如「抓包数据在哪」，按「切入文件 → 关键锚点 → 顺延到」三列依次在编辑器里搜一遍，确认能从一个文件走到下一个文件；八行都走通，就等于把这张主干图在自己机器上复现了一遍。

**这一段的收束**：到这一步，图上的每个方框都有了文件名与锚点：入口在 `lib/index.js` 的 `server.on(...)`，链在 `middlewares`，规则在 `lib/inspectors/rules.js`，抓包在 `lib/util/data-server.js`，出站与证书分别在 handlers 与 `lib/https/ca.js`。B 组后两篇要做的事，是把这张静态索引按时间展开——07 讲它们被装配的先后，08 讲装配好之后配置与进程如何保持同步；换句话说，本篇回答「在哪」，后两篇回答「何时」与「改了之后怎样」。带着这三个问题读源码，就不会在目录里迷路。

**从模型到代码这一步容易踩的坑**：领域基础四篇里的「代理形态」「TLS 中间人」「帧」都是按协议分层讲的，而源码是按模块职责分文件的，两套切法并不重合；若按协议顺序去找代码，会在 `lib/tunnel.js`、`lib/https/index.js`、inspectors 之间来回跳。本篇那张图其实是把两套切法对齐了一次：左边按「进门形态」分，中间按「加工次序」分，右边按「谁订阅数据」分。代价是要同时记住三套坐标；边界是它只覆盖主干，具体协议细节仍各归其专篇。

**为什么「代价与边界」值得反复写**：只记「四类入口 → 中间件链 → 事件总线」这条主线，遇到「新增一个协议要改几处」「为什么抓包不能决定转发」这类问题时仍会答不上来；把每个设计的「牺牲了什么、什么情况不适用」一并记住，才算真的把模型落到了代码上。后面两篇会不断回到这一点：一篇讲装配次序的代价，一篇讲进程隔离与配置单例的边界，三篇合起来才是完整答案。

**为什么 B 组是转折段**：领域基础给的是「应当如此」，架构这三篇给的是「实际如此、由谁承载、何时装配、改了会怎样」。术语密度也在这里陡增，遇到生词回概念精解查一次比硬猜更省时间；代价是要同时兼顾模型与代码两套坐标，边界是本篇只把方框钉到文件上，时间线留给下一篇。

**一个可带走的判断**：以后再看到「服务已经起来」这类描述，先问是端口就绪、业务就绪，还是插件就绪；本篇的图只保证「方框都在」，真正的先后要由下一篇的启动时序说明。把这个问题意识带到最后一篇，就能理解为什么配置改了不需要重启、却需要另铺通知路径——启动期只发生一次，运行期靠的是另一套机制。

## 常见误解

1. **容易以为图上的方框是四个独立进程或四套内核，其实四类入口共用同一个 `http.Server`、汇入同一条中间件链**：图的左右只是「消化协议差异」与「消化业务差异」两个视角，`lib/index.js` 里 `server.on(...)` 与 `middlewares` 挨着写就是证据；把方框数当成进程数，就会在「进程三层」一段里多算一层。
2. **容易以为 `proxyEvents` 只是抓包用的，其实它是注入每个中间件的 `this`、又经 `exportInterfaces` 暴露给插件与界面的内核总线**：抓包只是它最典型的用法；把它当成「抓包开关」，就解释不了插件为何能拿到内核能力，对照见[《易混淆概念辨析》](/concepts/08-confusions)。
3. **容易以为 pfork 子进程和 `--cluster` worker 都是「多开几个进程提速」，其实一个按功能隔离、一个按多核分担，且默认都不启用**：worker 共享主端口却不共享数据目录，pfork 子进程承载插件与后台服务、根本不碰主端口；混淆二者会误判默认进程数，见[《概念精解 · Node 运行时与内核骨架》](/concepts/04-runtime)。
4. **容易以为界面实时看到抓包是 WebSocket 推送，其实用的是 `cgi-bin/get-data` 的 100 / 900 ms 短轮询**：有新数据加快、空闲放慢，代价是始终存在最多一档间隔的延迟；这一档延迟不是「卡了」，而是省请求量的主动折中。

## 小结

- 四类入口共用单端口，经归一化后汇入同一条 Express 中间件链。
- 链序为 `lib/init.js` → `biz/index.js` → inspectors 四阶段 → 自定义中间件 → handlers 三类，全部 `bind(proxyEvents)`。
- `proxyEvents` 是内核总线，`exportInterfaces` 把它包装成对插件与界面可用的接口。
- 抓包靠 `request` / `frame` 事件广播与 `cgi-bin/get-data` 的 100/900 ms 短轮询。
- 进程分 CLI、detached 业务进程、pfork 子进程三层，`--cluster` 才启用多 worker。
- 本篇为 [《从 w2 start 到端口监听》](/architecture/startup) 准备了「图上每个方框对应哪个文件」的坐标：正因四类入口、中间件链与事件总线都已在图上定位，07 才能沿启动时序逐个把它们落到真实的初始化代码上。
