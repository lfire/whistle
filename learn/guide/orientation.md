# 站点导览与代码地图

第一次打开一个成熟的 Node.js 代理项目，最容易迷路的不是语法，而是不知道「哪个文件负责哪一段」。本节先固定版本基线，再给出一张可以按图索骥的代码地图，最后说明各板块解决什么问题。读完你应该能回答：一个请求进来先落到哪里、规则该去哪找、[抓包](/concepts/05-capture)数据存在哪里。 作为全站 01 号起点，本篇承接 [第 0 站 · 第一次跑通](/guide/quickstart) 的操作经验、但不预设你读过源码，只先回答「去哪找」这个坐标问题；后面 02–05 才逐层回答「是什么」，而把名词本身从零讲透的是概念精解 31–35，零基础读者可以先读那几篇再回来（路线见下方先修知识）。

::: tip 先修知识

给完全没接触过源码的读者补三个基本词：TCP 是传输层协议，只负责在两个端点之间可靠、有序地搬运一段字节流，并不关心字节里装的是什么；HTTP 是架在 TCP 之上的应用层协议，用一段有固定格式的文本描述一次「要什么 / 给什么」；HTTPS 不是另一种新协议，而是把同样的 HTTP 内容先做一次加密、再交给 TCP 传输，因此中间的代理默认只看见密文。后面 02–05 会把这三层逐一拆开。

## 站点基线：先把版本钉死

本站基于 `guide` 分支、提交 `3b85cebc4`、版本 `v2.10.13`（`package.json:4`）撰写，运行环境要求 Node.js `>= 16.0.0`（`package.json:77-78` 的 `engines`）。README 列出的能力是：对 HTTP、HTTPS、HTTP/2、WebSocket、TCP 抓包与改写；支持 HTTP、HTTPS、SOCKS、反向代理多种代理模式；内置 Weinre、Console、Composer；可通过[插件](/concepts/07-extension)扩展，也可作为 npm 模块引用（`README.md:17-30`）。

为什么开篇就强调基线？因为 [CONNECT](/concepts/01-proxy) 解密判定、叶证书有效期、HTTP/2 降级策略都随版本调整，脱离提交谈行号很容易对不上。本站所有 `路径:行号` 引用都以这个提交为准，若你检出的是其它版本，请以函数名和事件名作为锚点，而不是死记行号。需要补充的是，`3b85cebc4` 之后的提交只改动文档站 `learn/`，业务源码（`lib/`、`bin/`、`biz/` 等）零改动，因此这里的行号与函数名对得上当前仓库，不必换成文档站自身的提交号。

与官方 `docs/` 的分工也要先分清：`docs/index.md:1-20` 所在的官方文档站回答「怎么装证书、怎么写规则、怎么启动」，本站回答「这条规则在哪个函数被解析、为什么要这样设计」。遇到配置项语义查官方文档，遇到实现机制查本站，两者互补而不重叠。

**为什么这样设计**：把版本钉死，是为了替读者省掉一类最隐蔽的麻烦——源码里的分支条件、证书有效期、协议降级策略都会随版本改动，脱离提交去记行号，你翻到的函数可能和文档描述的不是同一份代码。把「与官方 `docs/` 分工」那句结论展开成推理就是：用法会随版本增删、且面向所有使用者，适合由官方文档统一维护；而「为什么这样设计」必须钉在具体函数上才有意义，本站因此选择锁死提交、只讲机制，两者互补而不重叠。

**代价与边界**：这套坐标只在 `3b85cebc4` 上精确有效，换版本就得改用事件名与函数名当锚点；它适合理解机制，却不适合查某个配置项的确切取值，后者仍要回官方 `docs/`。

**打个比方**：行号像门牌号、会随街区改建而变，函数名像店铺招牌、相对稳定；记招牌比记门牌更经得起翻修。

**自己验证**：按代码地图表的「建议时机」列，先打开 `index.js` 扫一眼入口，再顺着标着「主线」的行打开 `lib/index.js`，亲自走一遍「最先 → 主线」的顺序，就能体会目录坐标为什么比逐个翻目录省事。

这也是为什么本站反复强调「以函数名和事件名为锚点」：一旦有了稳定的参照物，行号漂移就不再影响阅读连续性。

## 代码地图

下表把仓库按目录切开。「建议时机」一列是阅读顺序建议，不是重要性排序。

| 路径 | 职责 | 关键文件 | 建议时机 |
|---|---|---|---|
| `bin/` | CLI、证书、系统代理 | `bin/whistle.js` | 看启动流程 |
| `index.js` | npm 包入口、cluster | `index.js` | 最先扫一眼 |
| `lib/` | 内核装配与配置 | `lib/index.js`、`lib/config.js` | 主线 |
| `lib/` | 初始化、隧道、升级 | `lib/init.js`、`lib/tunnel.js` | 主线 |

| `lib/rules/` | 规则引擎与存储 | `lib/rules/rules.js` | 看规则 |
| `lib/inspectors/` | 请求四阶段 | `rules.js`、`req.js`、`data.js`、`res.js` | 主线 |

| `lib/plugins/` | 插件加载与通信 | `lib/plugins/index.js` | 看扩展 |

| `assets/` | 静态资源 | `assets/js/` | 按需 |

为什么把 `lib/` 单独拆成三行？因为它是内核，而内核里又明显分成「装配」「协议入口」「连接管理」三簇，混在一起看会误以为它们平级。

**为什么这样设计**：代码地图按目录切、而不是按功能切，是因为读者最先想知道的是「某个文件在哪」——目录是唯一稳定、不随重构漂移的坐标；按功能切会随版本把同一个文件挪来挪去，反而更难查。把 `lib/` 单独拆成三行也出于同一逻辑：它内部明显分成装配、协议入口、连接管理三簇，混成一行会让人误以为三者平级。

**代价与边界**：代价是单看表格看不出调用关系，得靠「建议时机」列补一条阅读顺序，再用正文里「一次请求」的主线把散落的行串起来；换句话说，表格负责「定位」，主线负责「连通」，两者缺一不可。

**打个比方**：这张表像图书馆的索书号，先告诉你书架在第几排，正文才是书里的内容；「建议时机」是借阅顺序而不是重要性排名。

**自己验证**：任选表格里一行，先只看「关键文件」列写下它属于哪一类，再翻到正文里找它在「一次请求」主线的哪一段出现过，就能亲手验证「定位」与「连通」是两件事。

按编号顺读与按需跳读并不冲突：表格给的是坐标，不是必须逐格走完的清单。

## 怎么读这份源码

建议先领域、后源码。原因很直接：如果不先理解 CONNECT 隧道与两段 [TLS](/concepts/03-tls)，看到 `lib/tunnel.js` 的解密判定只会觉得是一堆布尔条件；先有模型，代码里的每个分支才有理由。

读的时候把仓库和文档并排打开，遇到 `lib/index.js:40-52` 这类引用就立刻跳过去看一眼，再回来接着读。以「一次请求」为主线串起各层，比按目录从头翻到尾有效得多：入口 → 中间件 → 规则 → 出站 → 抓包，这条线在后面的架构总览里会完整展开。另外，行号会随提交漂移，但 `server.on('connect')`、`app.use(mw.bind(proxyEvents))` 这类事件名和函数名相对稳定的锚点，值得优先记住。

**为什么这样设计**：「先领域、后源码」不是学习偏好，而是由代码本身的形态决定的：`lib/tunnel.js` 里的解密判定读起来只是一组布尔条件，只有先在脑子里有「CONNECT 隧道 + 两段加密连接」的模型，每个分支才有理由、才记得住。

**代价与边界**：代价是先花时间建立模型、不能立刻上手改代码；边界是这套方法适合理解机制，不适合查某个配置项的确切取值，后者该回官方 `docs/`。

**打个比方**：先看地图再进城市，路线里的每个岔口才有意义；直接扎进巷子，看到的只是互不相干的拐弯。

**自己验证**：遇到文中带行号的引用就立刻跳过去看一眼再回来，遇到 `server.on('connect')`、`app.use(mw.bind(proxyEvents))` 这类事件名与函数名则优先记住；隔一小段再回头核对，会发现行号会随提交漂移、而事件名依旧能用。

把「一次请求」当主线串起入口 → 中间件 → 规则 → 出站 → 抓包，比按目录从头翻到尾有效得多，这条线在后面的架构总览里会完整展开。

## 常见误解

1. **容易以为本站是官方使用文档的替代品，其实两者分工不同**：官方 `docs/` 回答「怎么装证书、怎么写规则、怎么启动」，本站回答「这条规则在哪个函数被解析、为什么这样设计」；遇配置项语义查官方文档、遇实现机制查本站。
2. **容易以为行号是稳定坐标，其实它会随提交漂移**：文中带行号的引用都钉在 `3b85cebc4`，换版本后应以 `server.on('connect')` 这类事件名和函数名为锚点，而不是死记行号。
3. **容易以为「建议时机」是重要性排序，其实它只是阅读顺序建议**：代码地图那一列标的是「什么时候看」，不代表 `lib/https/` 比 `lib/service/` 更重要，按需跳读同样成立。
4. **容易以为工程场景与概念精解必须最后读，其实二者是横向专题**：场景篇复用前四层机制，概念精解既可按编号顺读、也适合读任意章节时按词回查；成对概念的辨析见[《易混淆概念辨析》](/concepts/08-confusions)。
