# 弱网与异常注入：把偶发变成必现

线上偶发的超时、慢响应与 5xx 往往只在特定网络条件下出现，回到测试环境就消失。本篇以 Whistle 的延迟、限速、状态码与缓存规则为工具，把这类偶发问题改造成可重复触发的确定性场景，并沿源码说明规则从文本到请求的落点。读完你能独立搭出弱网与异常注入组合，也清楚每条规则在哪个阶段生效、在什么情况下不生效。[《复现、保存与重放》](/scenarios/reproduce-replay)（21）把一次偶现的真实流量固化成会话、还能反复重放，但重放复制的始终是「已经发生过的输入」；本篇承接这个未解问题，回答「现场里没发生过的失败」——超时、抖动、错误码与限流——如何不靠运气、用规则主动造出来并稳定复现。

::: tip 先修知识
本篇承接 [《复现、保存与重放》](/scenarios/reproduce-replay)（21），本篇会讲清（不需要预先掌握）：抓包会话按 reqId 定位、有界缓存会淘汰旧条目、Composer 重放是回打 Whistle 自身代理而非直连目标、以及规则在请求期与响应期分阶段生效。21 解决的是「把已经发生的现场存下来」，本篇把同一套规则链用来「制造一个从未发生的现场」。

若对规则 DSL、pattern、过滤器、优先级与热更新不熟悉，可先读 [《概念精解 · 规则 DSL 全景》](/concepts/06-rules)；对抓包、reqId、帧与旁路采样可查 [《概念精解 · 抓包数据面与帧》](/concepts/05-capture)；对 CONNECT 隧道与流量入口可查 [《概念精解 · 代理与流量入口》](/concepts/01-proxy)；对易混淆的阶段与时机可查 [《概念精解 · 易混淆概念辨析》](/concepts/08-confusions)。不要求预先读过源码，但知道「规则文本在解析期只被编译、请求期才逐条判定」会更容易跟上 chance 与时机分离那两段；忘记某个名词可查 [《全量术语索引》](/concepts/glossary)。

## 场景与痛点

移动端弱网验收。产品在高铁、电梯等场景下白屏或反复重试，而办公网络一切正常。需要把 3 秒请求延迟、5 秒响应延迟以及 3kb/s 限速固定下来，才能稳定观察加载态、骨架屏与超时提示是否按设计出现，而不是靠运气复现。

后端不稳定接口联调。依赖方接口偶发 500 或 429，客户端的重试与降级逻辑难以验证。用 `chance:0.5` 让一半请求返回 500，再对限流路径返回 429 并附带 `retry-after`，可以把容错分支从「等它自己坏」变成「每次都走到」。

维护与缓存演练。发布窗口需要验证维护页、缓存头与超时阈值。把域名整体改成 503 维护页、对静态资源设置长缓存、对接口禁用缓存，同时验证超时判定的边界（官方文档写 36 秒，源码启动参数却是 360000 毫秒，差异见「边界与坑」），能提前暴露客户端对缓存与超时的错误假设。

::: cols 20|30|50
| 规则 | 生效阶段 | 作用 |
|---|---|---|
| reqDelay | 转发请求前 | 延迟请求上行 |
| resDelay | 回写响应前 | 延迟响应下行 |
| statusCode | 请求期短路 | 不回源直接返回 |
| replaceStatus | 响应期 | 回源后替换状态码 |
:::

三条现场的「输入 → 动作 → 输出」是同构的：输入都是「只在特定条件下才出现的偶发现象」（高铁电梯里的白屏、依赖方偶发 500 / 429、发布窗口的缓存与超时）；动作统一为把网络条件写成可编辑的[规则 DSL](/concepts/06-rules)文本——延迟、限速、状态码、缓存各占一行；输出是「两次请求之间就能切换、每次都必现」的确定性场景。三者只在「要验证客户端的哪条分支」上分叉：加载态与骨架屏、重试与降级、缓存与超时阈值。

为什么这样设计：偶发问题难修，不是因为现象复杂，而是观察窗口不可控。把网络条件从「环境属性」变成「配置文本」，就不必真的去高铁、电梯里等信号，也不必把依赖方服务打挂；故障退化成一行可注释掉的规则，「可重复、可关闭」才同时成立——想关掉故障，删掉那条规则即可，不必去恢复一个被自己打挂的后端。这也正是 20 那条「短路转发」原则换到「失败」场景里的样子：让失败只发生在返回值里，不真的落在上游。

代价与边界：规则注入的是代理这一层的时序与响应，覆盖不到真实网络栈里的丢包、DNS 失败或运营商抖动；它证明的是「客户端拿到这些条件会怎么表现」，不是「这条链路在真实弱网里真的通」。因此弱网验收里能稳定看到加载态，不等于上线后弱网一定没问题，两者要分开记录。

类比：像用可调电源模拟电压跌落，不必真去等一次电网故障，还能把「跌到多少伏、持续多久」精确复现；但电源模拟不出整片电网的连锁反应，对应这里覆盖不到的真实网络栈行为。

最小自验：对照 `www.example.com/path reqDelay://3000` 与 `www.example.com/path2 reqDelay://5000 enable://abort` 两行，前者只是慢 3 秒、后者延迟 5 秒后直接掐断；用这两条现成配置就能自己说出「延迟」与「延迟后中断」的区别，不必真去断网。再看表格里 `reqDelay` 在「转发请求前」、`resDelay` 在「回写响应前」，就能自验「上行慢」和「下行慢」不是一回事。

三条痛点与后文四段配置也对得上：移动端「延迟 + 限速 + 中断」对应 reqDelay / resDelay / reqSpeed / resSpeed 那两段，联调「概率 500 / 429」对应 statusCode 与 replaceStatus 那段，维护演练「长缓存 / 禁用缓存 / 超时」对应 cache 与 disable 那段。先看痛点，就知道四段不是四种并列语法，而是三类约束各自逼出来的写法；表格里「生效阶段」那一列，正是后文「时机分离」那条原则的提前预告。

按角色看也清楚：移动端验收要的是「时序可控且能反复看同一帧」，后端联调要的是「容错分支每次都走到」，发布演练要的是「缓存与超时阈值能被主动触到」。三者能同时满足，是因为它们分别压在时序、状态码、缓存三个不同维度上，而规则文本恰好能把这三个维度各自写成一行；表格按「生效阶段」而非按协议名分列，也是为了先把维度摆正。

反过来想，若不做「把条件写成规则」这一步，就只能靠真的去弱网环境、真的把依赖方打挂来碰运气，而这两种做法都无法「关掉即恢复」——本篇全部配置的起点，正在这里。也正因条件是文本，同一条 `reqDelay://3000` 才能在两次请求之间被注释掉、把现场还原，而不必像 21 那样依赖一次再也回不去的真实流量。

## 可复制的配置


> **动手前**：下面的配置都写在 Whistle 界面的 **Rules** 面板里（Create 新建 → 粘贴 → Save → ON 开启）。如果还没把工具跑起来，请先完成 [第 0 站 · 第一次跑通](/guide/quickstart)：安装、启动、界面、代理、根证书与命中验证都在那里；否则照抄这些规则也看不到结果。

以下规则可直接粘贴到 Rules 面板，按需要叠加 `includeFilter` 或 `excludeFilter` 收窄命中范围，避免误伤同一域名下的其它请求；调试结束把对应行注释掉即可恢复，不必改动任何业务代码。延迟与中断成对使用，可以在延迟结束后直接掐断连接，模拟「请求发出但永远收不到结果」。

```txt
# 来源：docs/docs/rules/reqDelay.md
www.example.com/path reqDelay://3000
www.example.com/path2 reqDelay://5000 enable://abort

# 来源：docs/docs/rules/resDelay.md
www.example.com/path resDelay://3000
www.example.com/path2 resDelay://5000 enable://abortRes
```

固定毫秒值只能覆盖单一时序，官方给出用 `reqScript` 动态生成规则，随机落在 1 至 6 秒之间。

````txt
# 来源：docs/docs/rules/reqDelay.md、reqScript.md
``` delay.js
rules.push(`* reqDelay://${1000 + Math.ceil(5000 * Math.random())}`);
```
www.example.com/path reqScript://{delay.js}
````

状态码与响应改写分属两个时机：`statusCode` 在请求期短路，`replaceStatus` 先回源再改码。

```txt
# 来源：docs/docs/rules/statusCode.md
www.example.com/api/unstable statusCode://500 includeFilter://chance:0.5

# 来源：docs/docs/rules/replaceStatus.md
www.example.com replaceStatus://503 resBody://(<h1>系统维护中...</h1>)
www.example.com/api/rate-limited replaceStatus://429 resHeaders://retry-after=60
```

限速单位是 kb/s，请求体与响应体分别由两条规则控制。

```txt
# 来源：docs/docs/rules/reqSpeed.md、resSpeed.md
www.example.com/path reqSpeed://3
www.example.com/path resSpeed://3
```

缓存与超时属于边界条件注入，用来验证客户端是否遵守服务端约定。

```txt
# 来源：docs/docs/rules/cache.md
https://example.com/static cache://3600
https://example.com/api cache://no-cache

# 来源：docs/docs/rules/disable.md（官方示例 wwww 系笔误，本站用 www）
www.example.com/path disable://cache
pattern disable://timeout
```

把四段规则收拢成「输入 → 动作 → 输出」：输入一行写明 URL、指令与值的规则（可叠加 `includeFilter` / `excludeFilter` 收窄命中范围）；动作是 Rules 面板按行解析、把固定毫秒值或 `reqScript` 动态值绑到请求期或响应期的具体阶段；输出是「延迟结束后继续转发或直接掐断」「请求期短路返回 500」「按 kb/s 分块节流」「按 cache 值重写缓存头」等确定行为。调试结束把对应行注释掉即可恢复，整条链不必改动任何业务代码。

为什么这样设计：把延迟与中断成对给（`reqDelay` + `enable://abort`、`resDelay` + `enable://abortRes`），是因为「慢」和「永远收不到结果」是两类不同的失败，客户端分别对应「加载态 / 骨架屏」与「超时提示 / 重试」两套分支；只给延迟覆盖不了后者。状态码又拆成 `statusCode`（不回源）与 `replaceStatus`（先回源再改码），也是为了让「验证客户端对空响应体的处理」和「验证真实响应被改码」各有对应工具，不至于用错阶段。

把「固定毫秒值只能覆盖单一时序」这句展开：一行 `reqDelay://3000` 每次都恰好慢 3 秒，客户端可能刚好卡在某个缓存或重试窗口里，换一台设备就表现不同；官方才给出用 `reqScript` 随机落在 1 至 6 秒之间的写法，让同一条规则覆盖更多时序。但随机值只是「铺开覆盖面」，回归复现仍要回到确定性规则——两者互补而非替代，这也是「背后的设计思想」里概率过滤器与确定性规则分工的由来。

代价与边界：限速单位是 kb/s 且只作用于有 body 的流量（详见「边界与坑」），把它套到 `CONNECT`、204 上是拿错工具；`cache://3600` 与 `cache://no-cache` 验证的是「客户端是否遵守服务端约定」，不能证明缓存真的在代理层生效。规则靠「注释掉对应行」恢复，意味着没有版本回滚，多人共用一套 Rules 面板时容易互相覆盖，这与 25 要讲的协作与配置管理正好接上。

类比：像调音台上一排推子，延迟、限速、状态码、缓存各管一路，可以单独推也可以叠加，但推的是「送进代理的那一版信号」，不动业务代码这条总线；推完不复位，下一个人来看到的还是你留下的调音。

最小自验：把 `www.example.com/api/unstable statusCode://500 includeFilter://chance:0.5` 与 `www.example.com replaceStatus://503 resBody://(<h1>系统维护中...</h1>)` 对照——前者不回源、带概率，后者先回源再改码还补了正文；两条现成规则就能自验「请求期短路」与「响应期改写」不是一回事。再把 `disable://cache` 与 `disable://timeout` 放一起看，理解「缓存」和「超时」是两类边界条件，而不是同一种开关。

反过来想，若把延迟与中断合并成一条「慢一点再断」的规则会怎样：客户端究竟该显示加载态、骨架屏还是超时提示，就取决于实现里写死的那一个时序，调试者无法分别验证两套分支。拆成 `reqDelay` / `resDelay` 与 `enable://abort` / `enable://abortRes` 两对，正是把「什么时候慢」和「要不要给结果」拆成两个独立旋钮；同理 `statusCode` 与 `replaceStatus` 拆开，也是把「不回源」和「回源后改码」两种完全不同的输入分开。可复制的配置之所以看着条目多，不是语法杂，而是每个旋钮只管一件事。

把「叠加 includeFilter 或 excludeFilter 收窄命中范围」这句展开：延迟、状态码本身不挑请求，真正决定「哪些请求被注入」的是过滤器；所以同一批规则既能对单台设备生效、又不误伤同域名下的其它接口，靠的是把命中范围与注入动作拆成两层。若把范围写死在 URL 里，一个域名下多接口就得复制一整批规则，改动时极易漏掉其中一条——这也解释了为什么本篇反复提醒「调试结束把对应行注释掉即可恢复」：恢复的是动作，范围一直由过滤器单独管着。

## 背后的设计思想

[可观测性优先](/domain/debugging-workflow)：偶发问题难修，是因为观察窗口不可控。Whistle 不改动业务代码，而是把网络条件变成可编辑的规则文本，延迟、限速与状态码都可以在两次请求之间切换，于是「偶发」被压缩为「按配置必现」，[抓包](/concepts/05-capture)列表里也能同步看到规则命中情况。

[过滤器在解析期编译、请求期判定](/modules/rules-engine)：`chance:0.5` 在 `lib/rules/rules.js:1549-1739` 只被编译成 `{ key: 0.5 }` 匹配器，真正的 `Math.random() < key` 判定在每次请求命中的 `matchFilter`（`lib/rules/rules.js:1878-1885`）里现算，各次请求互不记忆。解析与执行分离，使同一条规则文本无需重复解析就能对大量请求逐条判定，也让包含/排除过滤器能和其他指令自由组合；代价是「50%」只是统计意义上的近似，短时间内的实际命中次数可以明显偏离一半。

[请求期与响应期时机分离](/modules/protocol-catalog)：`reqDelay` 卡在转发前，`resDelay` 卡在回源后；`statusCode` 不回源，`replaceStatus` 必须先拿到真实响应。指令被绑定到明确阶段，才不会用错工具——想验证客户端对空响应体的处理，就不能拿 `replaceStatus` 代替 `statusCode`。

[内存有界优先](/core/capture-data)与[中断能力由界面反向下发](/modules/webui)：长时间挂起的连接会持续占用抓包内存，因此除了超时兜底，界面还能主动中断。规则描述「要发生什么」，界面描述「现在停掉哪一条」，两者通过请求编号汇合，既保证观测数据有界，也让调试者随时收回控制权。

四条原则拼起来正好是一条链：可观测性优先解释「为什么把网络条件写成规则文本」，过滤器解析期编译 / 请求期判定解释「为什么概率规则能低成本复用」，请求期与响应期时机分离解释「为什么选错阶段就得不到预期结果」，内存有界与界面中断解释「为什么挂起的连接不会拖垮抓包」。少任何一条，前面那些可复制的配置就退回到「照着抄」。

输入 → 动作 → 输出：输入一条带 `chance`、`reqDelay`、`statusCode` 的规则文本 → 解析期把过滤器编译成匹配器、按 `isReq` / `isRes` 组装到请求期或响应期 → 请求到来时逐条判定、命中即在对应阶段延迟 / 限速 / 短路 / 改写 → 输出被注入了失败的请求与响应，以及抓包列表里可同步看到的命中情况。

为什么这样设计：过滤器在解析期只编译成 `{ key: 0.5 }`、请求期才用 `Math.random() < key` 现算，是为了让同一条规则文本不必重复解析就能对大量请求逐条判定，也让包含 / 排除过滤器能和其他指令自由组合；若把概率在编译期就算死，一条规则发出去就永远是同一个结果，「50%」也就无从谈起。请求期与响应期时机分离，则保证「想验证客户端对空响应体的处理」时不会误用 `replaceStatus` 去代替 `statusCode`——两者拿到的输入根本不是同一份。

代价与边界：概率是统计意义上的近似，短时间内实际命中次数可以明显偏离一半，且各次请求互不记忆——它适合铺开时序覆盖，不适合做「恰好一半」的精确断言。界面主动中断要按请求编号（[reqId](/concepts/05-capture)）把「停哪一条」与具体连接对上，规则文本管「要发生什么」、界面管「现在停掉哪条」，两者缺一，长时间挂起的连接就会持续占用抓包内存；这也是为什么这一节把「内存有界」和「界面反向下发」并列成一条。

类比：像舞台灯光预设，脚本（规则）写「第二幕灯渐暗、随机闪一下」，控制台（界面）另有一排急停按钮；预设可以反复用，急停则由人按当下这一场决定，谁也替不了谁。

最小自验：对照 `chance:0.5` 那条，连发十次并在心里记命中次数，若不是恰好五次也不必怀疑规则写错——这正是「每次请求独立掷一次、只保证统计近似」的自验；再对照表格里 `reqDelay` / `resDelay` 分列「转发请求前 / 回写响应前」，就能确认阶段分离。把「规则描述要发生什么」与「界面描述现在停掉哪一条」两句话放一起，也能自己说出它们为什么必须靠请求编号汇合。

再把「解析期与请求期分离」往反面推一步：若 `chance` 在编译期就掷一次骰子，那么整条规则在此后所有请求上都只有同一个结果，「一半请求返回 500」就退化成「要么全返回、要么全不返回」；把判定挪到每次命中的 `matchFilter` 里现算，才让「同一条规则文本、大量请求、逐条不同结果」成立。代价也很直接——既然每次独立，就无法保证短窗口内恰好一半，也不能靠「前几次没命中」推断「下一次该命中了」；这正是概率过滤器适合铺覆盖面、却不适合做精确断言的原因。

把「请求期与响应期时机分离」也推一步：`reqDelay` 卡在转发前、`resDelay` 卡在回源后，若把两者都实现成「响应回来之前 sleep」，上行延迟就永远验证不了客户端的请求超时与重试策略，只能看到下行慢。指令被绑定到明确阶段，才让「改哪个字段」与「观察哪条分支」一一对应；代价是阶段一旦选错，现象看起来就像「规则没生效」，排查得先回到表格那列「生效阶段」，而不是反复改毫秒值。

## 源码链路

1. **入口 · 过滤器编译**：`lib/rules/rules.js:1549-1739` 的 `resolveMatchFilter` 把 `m:`、`b:`、`chance:` 等前缀拆成带 `isInclude` / `not` 的匹配器（`:1655` 把 `chance` / `probability` 单独归为概率类，不当请求头处理），请求到来时 `lib/rules/rules.js:1985-2009` 的 `matchExcludeFilters` 逐条调 `matchFilter`（`:1819-1982`）；后者在 `:1878-1885` 用 `Math.random() < key` 当场判定，`key` 以 `%` 结尾时先除以 100。所以 `chance` 是每次请求独立掷一次的过滤器，既不排程也不累积命中。参见[规则引擎：解析与匹配](/modules/rules-engine)。
2. **规则解析 · 阶段组装**：`lib/rules/rules.js:2239-2299` 的 `resolveRules` 按 `isReq` 与 `isRes` 挑选协议表，把命中结果写入 `req.rules`，请求期与响应期各取一份。参见[指令体系与分发链路](/modules/protocol-catalog)。
3. **应用点 · 延迟与限速**：`lib/inspectors/data.js:544-550` 把 `reqDelay` 交给 `util.delay` + `setDelayTimer`，延迟结束才 `next()`，期间 `needAbortReq` 为真就 `res.destroy()`；`lib/inspectors/res.js:1162-1173` 同理先延迟再 `res.src(...)`，`needAbortRes` 为真则记下已存头后销毁。速度值由 `lib/inspectors/req.js:520-524` 与 `lib/inspectors/res.js:910-914` 写进 `data.speed`（kb/s），再分别经 `WhistleTransform`（`lib/util/whistle-transform.js:12,109-112`，请求体）与 `SpeedTransform`（`lib/util/speed-transform.js:9,29-35`，响应体）按 `chunk.length * 1000 / (speed*1000/8)` 毫秒逐块延时——限速是按字节流分块节流，不是把整段响应一次性 sleep。参见[一次 HTTP 代理请求的旅程](/core/http-request)。
4. **应用点 · 状态码短路**：`lib/util/index.js:3576-3599` 的 `getStatusCodeFromRule` 只对 `rule.isSpec` 生效，产出 `{ statusCode, headers }`；`lib/inspectors/res.js:1313-1319` 在拨出站前取到它就直接 `res.response(util.wrapResponse(svRes))` 并置 `Connection: close`，`statusCode` 因此不产生回源流量。参见[一次 HTTP 代理请求的旅程](/core/http-request)。
5. **回写 · 响应期改写**：`lib/inspectors/res.js:819-825` 用 `replaceStatus` 改写状态码，`lib/inspectors/res.js:870-891` 按 `cache` 值重写 `cache-control` 与 `expires`。参见[抓包数据的采集与上报](/core/capture-data)。
6. **上报 · 界面中断**：`biz/webui/cgi-bin/abort.js:6-22` 接收前端的 id 列表（单次最多 1200 个，`:4,11-14`），对每个 id 同时调 `proxy.abortRequest`（`lib/util/data-server.js:642`，触发 `item.abort()`）与 `socketMgr.abort`（`lib/socket-mgr.js:859` 导出的 `destroy`，`:849-857` 删 `conns[reqId]` 并销毁 req/res 流）。参见[Web 管理界面](/modules/webui)。

把 1–6 收拢成「输入 → 动作 → 输出」：输入一条带 `chance` / `reqDelay` / `statusCode` / `cache` 的规则 → 过滤器编译成匹配器、`resolveRules` 按阶段组装、请求到来逐条命中 → 延迟 / 限速 / 短路 / 改写落在各自的 inspector → 界面按 id 下发中断 → 输出「按配置必现的失败」与「可随时收回的控制权」。六步不是六个并列模块，而是同一条规则从文本到连接、再到被界面收回的六个工位。

为什么这样设计：第 3 步的限速不是把整段响应一次性 sleep，而是按 `chunk.length * 1000 / (speed*1000/8)` 毫秒逐块延时；因为「3kb/s」描述的是持续速率而不是总时长，只有按字节流分块节流，长响应和短响应才都表现为同一个速率。第 4 步 `statusCode` 在拨出站前就 `res.response(...)` 并置 `Connection: close`，是为了让「500」完全不产生回源流量——否则依赖方服务真会被打到，容错验证就变成了制造真实故障。

代价与边界：阶段绑定得越明确，选错工具的代价也越明确——想验证空响应体却用了 `replaceStatus`，会先白跑一次回源；限速逐块延时意味着大量小 chunk 会带来可观的定时器开销。第 6 步界面中断单次最多 1200 个 id，是「一次能收回多少」的上限，超出要分批；`destroy` 删掉 `conns[reqId]` 并销毁 req/res 流之后，这条请求在抓包里留下的仍是「被中断」的状态，而不是一条完整响应，排查时别把它当成服务端返回。

类比：像工厂流水线，第 1–2 步是排版与分拣，第 3–5 步是各工位的加工，第 6 步是质检台上的急停拉绳；每件货按预定工位走，拉绳则随时能把在制的那几件停下来，停下来的货不会假装已经装箱。

最小自验：把第 1 步「`chance` 每次请求独立掷一次」与第 4 步「`statusCode` 不产生回源流量」对照——前者解释为什么命中次数会波动，后者解释为什么 `statusCode://500` 不会真把上游打挂；两处都用本篇已有的规则文本即可自证，不必去翻定时器实现。再把第 6 步「界面按 id 下发中断」与「背后的设计思想」里「规则管要发生什么、界面管停掉哪条」对照，就能理解两个视角如何在同一个请求编号上汇合。

按 1→6 排查「注入没生效」可以这样问：过滤器有没有被编译成匹配器、还是被当成请求头（第 1 步）→ 这条指令落到了请求期还是响应期（第 2 步）→ 延迟 / 限速 / 短路有没有在对应 inspector 上挂上（第 3 步）→ `statusCode` 是不是被别的高优先级规则盖过（第 4 步）→ 响应期改写有没有作用到有 body 的响应（第 5 步）→ 是不是被界面提前中断了（第 6 步）。逐段问下来，比反复改那个毫秒值有效得多。

六步与七段模板里「源码链路」一节是同一条链的两种粒度：模板给的是「入口 → 规则解析 → 应用点 → 回写/上报」的粗线，本篇细到过滤器编译、阶段组装、延迟限速、状态码短路、响应期改写、界面中断六个工位。其中第 4 步最容易被跳过——`statusCode` 是在拨出站前就短路、而不是把上游返回的码改掉，这正是「注入 500 不会真把服务打挂」在链路上的落点；读的时候要特意停一下，别把它和响应期的 `replaceStatus` 混成一个工位。

按阶段归位也更清楚：第 1–2 步管「规则怎么被编译与命中」，第 3–5 步管「失败具体落在哪一段流」，第 6 步管「调试者怎么收回控制权」。三层互不重叠，所以想调概率分布不必动限速实现，想改中断上限也不必碰过滤器；这也是本篇把「可复制的配置」与「源码链路」分成两节、却反复互相回指的原因。

## 边界与坑

- 限速只作用于有 body 的流量：`reqSpeed` 对 `CONNECT`、`UPGRADE` 及 204 等无响应体的请求无效（`docs/docs/rules/reqSpeed.md`）；`resSpeed` 对 `GET`、`HEAD`、`CONNECT`、`UPGRADE` 等无请求体的请求无效（`docs/docs/rules/resSpeed.md`）。两处官方措辞按「无请求体 / 无响应体」分别列举，容易误读；从源码看真正的分界是流方向：`reqSpeed` 节流请求体（`lib/inspectors/req.js:520-524,560` 挂 `WhistleTransform`），`resSpeed` 节流响应体（`lib/inspectors/res.js:910-914,1004` 挂 `SpeedTransform`，`:1099-1100` 在无响应体时直接 `delete data.speed`）。
- `statusCode` 默认返回空响应体，需要正文必须叠加 `resBody`；返回 401 时浏览器默认弹出认证框，应加 `disable://userLogin`（`docs/docs/rules/statusCode.md`）。
- `chance` 是按 `Math.random() < key` 命中的概率过滤器，取值 0 至 1（`docs/docs/rules/filters.md:25,32`），源码在 `lib/rules/rules.js:1878-1885` 每次请求独立比较一次；不是定时器，也不会随时间累积命中，更不会按请求顺序轮流命中。
- 超时口径要三处对照，别只按一个数字推断：官方 `docs/docs/rules/disable.md:114` 写「默认 36s 内无数据传输判超时」并给出 `disable://timeout`；启动参数 `-t/--timeout` 默认 `360000` 毫秒（360 秒，`docs/docs/cli.md:43`、`package.json:9`），由 `lib/index.js:44` 写入 `server.timeout`；`lib/inspectors/res.js:18,650-655` 另有 16 秒的 socket 连接建立超时。源码中没有找到独立的 36 秒请求级定时器，因此遇到超时问题应先确认实际生效的是哪一处，官方文档的 36 秒不宜当作精确阈值使用。
- 对 204、304 等无响应体的状态码，`resBody` 一类 body 改写不生效（`docs/docs/rules/resBody.md`）。

- **容易以为 `reqDelay` / `resDelay` 只是「让请求慢一点」，其实前者卡在转发请求前、后者卡在回写响应前**：生效阶段不同，配错阶段就看不到预期时序；表格里那列「生效阶段」正是给这条辨析用的。
- **容易以为 `statusCode://500` 真的回源拿了 500，其实它在请求期短路、不回源直接返回**：默认还是空响应体，需要正文得叠加 `resBody`；`replaceStatus` 才是先回源再改码。
- **容易以为 `chance:0.5` 会精确让一半请求命中，其实它每次请求独立比较一次 `Math.random() < key`**：只是统计意义上的近似，既不排程、不累积，也不会按请求顺序轮流命中。
- **容易以为 `reqSpeed` / `resSpeed` 对任何请求都生效，其实 [CONNECT](/concepts/01-proxy) 这类隧道与 204 等无响应体的请求会被整段跳过**：从源码看真正的分界是流方向，两条规则分别节流请求体与响应体；更细的对照可见 [《概念精解 · 易混淆概念辨析》](/concepts/08-confusions)。

把这一节五条既有坑与上面四条辨析分开看，会更清楚该记什么：五条坑是官方或源码划定的事实边界（限速只作用于有 body 的流量、`statusCode` 默认空响应体、`chance` 取值 0 至 1、超时三处口径、204 / 304 无响应体），照着改就能绕过；四条辨析是读者心里默认错的模型（延迟只是变慢、500 真回源、概率精确一半、限速对所有请求生效）。前者是「怎么写才对」，后者是「这条链究竟怎么走」，后者只能靠把源码链路走通来纠正，光看配置文本改不出来。

## 小结

- 弱网注入的核心不是「更慢」，而是把不可控的网络条件转成可重复的规则文本。
- 延迟、限速、状态码、缓存分别落在请求期、响应期与回写期，选错阶段就得不到预期结果。
- 过滤器在解析期编译、请求期判定，是概率规则能低成本复用的前提。
- 超时兜底与界面主动中断共同保证挂起连接不会无限占用抓包内存。
- 概率过滤器与随机脚本负责覆盖时序，确定性规则负责回归复现，两者互补而非替代。
- 本篇为 [《HTTPS、证书与鉴权的排障现场》](/scenarios/https-trust) 准备了「失败可以被主动注入成必现」这个前提：既然超时、错误码与限流都能写成规则稳定复现，23 就顺势回答一个更靠前的问题——当这些注入规则遇上 HTTPS 隧道，请求究竟有没有被解密、规则是否真的作用在明文上。
