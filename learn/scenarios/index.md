# 工程场景总览：从问题到设计思想，再到代码

读完了原有主线板块，很多人仍会在真实工程里卡住：知道 `host` 怎么解析，却不知道把整站代理到本地 dev server 时排除规则该怎么写；知道 `file` 会在 handler 里短路，却不知道接口尚未就绪时如何把 Mock 稳定固化下来。原有主线按「领域基础 → 全局架构 → 核心链路 → 模块深潜 → 进阶实践」纵向展开，回答的是「这段代码实现什么」；新增的「工程场景」专题换一个方向，从真实工程问题出发，向上追溯到整体业务设计思想，向下追溯到工程实现代码细节。它插在「模块深潜」与「进阶实践」之间，是一组横向专题：每个场景都能在官方文档、集成测试或源码 CGI 中找到真实出处，读完不仅会配规则，还能说清这条规则为何这样落地、边界在哪里。紧接着 13–17 把规则引擎、指令分发、证书、插件与 Web 界面逐块拆完实现之后，留下的空白正是「代码会读了，遇到一个真实工程问题却仍不知从哪条原则想起」；本篇不新增实现细节，而是把视角从「这段代码做什么」翻转为「这个问题该由哪条设计回答、又落到哪段代码」，读完你能拿任何一个手头问题，用下面的五层追溯法定位到该精读的场景篇。

## 追溯方法：五个层次

本层每篇文档都按同一条链展开，读者可以把它当成一把尺子，去量任何一个新问题。

1. **工程问题**：谁、在什么系统约束下、遇到什么具体现象。场景不凭常识编造，一律来自 `docs/docs/` 的使用文档、`test/` 的集成测试或 `biz/webui/cgi-bin/` 的真实工作流。
2. **设计原则**：这个问题之所以被这样解决，背后是 Whistle 的哪条整体取舍。原则不是口号，必须能链接回站内已有章节，例如 [观测不改道](/core/capture-data)、[顺序即优先级](/modules/rules-engine)、[默认透传、显式才解密](/core/connect-mitm)。
3. **内核机制**：原则落到哪一层实现——入口中间件链、规则编译与匹配、协议分桶、handler 短路，还是 service 子进程。
4. **源码位置**：机制对应的 `lib/xxx.js:行号`，并链接到对应的核心链路或模块章节，例如 [一次 HTTP 代理请求的旅程](/core/http-request)、[规则引擎](/modules/rules-engine)。
5. **边界**：官方 FAQ 或源码阈值划定的失效条件，例如 2MB 合并上限、600 条抓包缓存、100 次重放上限。

对应到文档结构，就是固定小节「场景与痛点 → 可复制的配置 → 背后的设计思想 → 源码链路 → 边界与坑」。前三步回答「为什么」，后两步回答「凭什么」。把这条链走通，规则就不再是需要背下的字符串，而是能从设计推出来、又能被源码验证的结论。

把五层当成一条流水线，它的「输入 → 动作 → 输出」是：输入一个带约束的工程现象（谁、在什么系统下、看到什么），动作是依次追问「这该由 Whistle 的哪条取舍回答」（设计原则）→「这条取舍落在哪一层实现」（内核机制）→「对应哪个文件与哪几行」（源码位置）→「什么时候会失效」（边界），输出则是一条既能从设计推出来、又能被源码验证、还标好了失效条件的结论。第 1 步要求现象有真实出处、第 2 步要求原则能链接回站内已有章节，正是为了不让任何一跳变成凭印象的猜测。

为什么这样设计：主线 01–17 走的是「代码 → 结论」的正向推导，读起来顺，但遇到一个从没见过的新问题时没法反查——你不知道该翻哪个文件。五层法把方向掉过来，变成「问题 → 结论 → 代码」的反向定位：先想清楚该由哪条原则回答，再拿着原则去源码里找证据，比在几万行里全文盲搜快得多。「为什么」放在「凭什么」之前，也是因为先有设计上的预期，源码阅读才有靶子，不至于读完一段代码仍不知道它要解决什么。

代价与边界：这套方法依赖「原则能链接回站内已有章节」这个前提。一个本站尚未成篇的新机制，走到第 2 步就会卡住，只能退回从源码读起；它给的是一条定位路径，不是实现全貌，真要改代码仍得回主线篇章逐行看。另外前三步是推理、后两步是举证，缺了后两步，结论就容易停在「听起来合理」而没被验证过。

类比：它更像查字典——先按部首（设计原则）把范围缩到某一页，再看字号（内核机制）与页码（源码位置），最后翻到这一页的勘误（边界）；不带索引地逐页翻正文，相当于全文搜索。

最小自验：不用跑任何命令，拿手头一个工程问题，先在下面「设计原则速查」表里挑出最像的一条原则，再到「场景地图」表里定位到该读的场景篇；若两张表指向同一处，说明这条反向链已经走通，可以带着「它为什么这样设计」的问题进正文了。

五层与后面每篇固定的七段模板是一一对应的：「场景与痛点」承载工程问题与系统约束，「可复制的配置」把现象固化成可复现的输入，「背后的设计思想」同时回答设计原则与内核机制，「源码链路」给出源码位置，「边界与坑」收拢失效条件。前三节答「为什么」、后两节答「凭什么」，正好是上面那句结论在文档结构上的落地——模板不是随意定的栏目，而是五层法的排版投影。

一条走通了的结论怎么验收？它应当能同时回答三问：为什么这样设计（能链接回一条原则）、代码在哪（能指到一处实现）、何时会失效（能说出一个阈值或前提）。三问缺一，说明五层还没走完，此时的「我会配这条规则」仍停留在记忆层面，换个现象就会卡住；这也是本层反复要求「结论要能被源码验证」的原因。

反过来想，若跳过第 2 步直接搜源码，会陷进「哪个文件都可能相关」的困境：一个「接口没写好」的现象，可能牵到规则解析、协议分桶、handler、响应改写好几处，没有原则作靶子就只能逐文件试。若只抄配置、不看边界，又会把示例当成普适结论，一遇到 2MB 合并上限或 600 条抓包缓存就失效而不自知。两种偷懒对应的正是第 2 步与第 5 步，缺哪步就在哪步还债。

这十条并非并列：前两条界定「代理看不看得到」，中间三条界定「规则怎样被解析与生效」，后五条界定「数据、进程与信任的边界」。每篇场景文档只会取其中三到四条重点展开，其余作为背景约束存在。

为什么先把原则抽成一张表：本层有 9 篇场景，若各写各的理由，读者很难看出「观测不改道」与「默认透传、显式才解密」其实是同一条「默认不做例外」的两种表现，也看不出「内存有界」和「零复制优先」都在为同一个数据面服务。共用一张表，等于给 9 篇装了同一套词汇，跨篇对照才成立；否则每篇都要重讲一遍前提。

输入 → 动作 → 输出也很直接：输入是某一个场景，动作是查表找出它主要压在哪几行原则上，输出是「这一篇会重点展开哪三到四条、其余只作背景」的预期；带着这个预期读正文，就不容易被局部细节带偏，也能一眼看出某条原则在哪些场景里反复出现。

代价与边界：表里「代表源码」省略了目录前缀，且每行只给一处代表位置，它是索引而不是完整证据链，要核对细节必须进各篇「源码链路」。十条也是按本层需要挑的，并不等于 Whistle 只有十条设计原则，没进表的取舍只是这几类问题恰好用不上；把这张表当全集，反而会漏掉别的机制。

类比：像一张地铁线路图，只标换乘站与线路名，不标每一站的到站时刻；真要坐车，还得看各篇「源码链路」那张详图。

这张表还有个具体用法：先按你手头的现象在「覆盖场景」列里找分组，再横向读同一行的「一句话」，就能预判这篇会拿哪条原则当主线；读完正文后回头对表，还能检查自己是否把背景约束误当成了重点。它因此既是入口索引，也是读完之后的核对清单，而不是只供扫一眼的装饰。

十条之所以分成三组，是因为它们回答的是三个不同层次的问题：前两条界定「代理看不看得到」，中间三条界定「规则怎样被解析与生效」，后五条界定「数据、进程与信任的边界」。把「观测不改道」和「默认透传、显式才解密」放在一起看，会发现它们是同一条「默认不做例外」在抓包与解密两处的不同措辞；分组的用意就是让这种同源关系显出来，免得十条被当成互不相干的口号各背一遍。

这 9 篇不是操作手册的目录，而是「问题类型」的目录：同一条 `file://` 规则，在「本地联调」里是目录映射，在「Mock」里是内联短路，在「复现」里是会话导出后重放的输入。分类的用意，正是逼出同一机制在不同约束下的不同用法。

把上面这句结论展开：规则文本本身并没有变，变的是三件事——`value` 由谁提供（本地目录 / 内联值 / 导出的会话）、请求有没有真的出站、以及这次响应要不要留档复用。设计原则是常量，工程约束是变量，所以分类必须按「约束」而不是按「协议名」；若按协议名分篇，一个现象往往牵涉三四个协议，读者还是得自己拼，等于没回答「我该读哪篇」。这正是从「实现视角」翻到「工程视角」的关键：工程里先冒出来的是现象（页面 404、证书不受信任、偶现超时），不是「我要用某条规则」。18 这一页之所以叫总览，就是因为要先帮读者完成这次视角翻转，再进具体场景。

这张地图的「输入 → 动作 → 输出」可以这样用：输入一个真实现象；动作是先按「改道 / 未就绪 / 偶现 / 加密与真机 / 多人协作」判断它落在哪一分组，再看同组相邻篇的分工——例如 23 先解决「看不看得见」（证书信任与 Tunnel to 排障）、24 才解决「流量怎么来」（手机接入与页面内调试），25 管「配置怎么存」（规则分组与共享）、26 管「怎么自动验」（CI 内嵌与断言）、27 收尾「哪里会失效」（阈值与默认行为）；输出是「该精读哪一篇、以及它前后各依赖谁」。分组名因此不是功能模块名，而是问题类型名。

为什么这样设计：按问题类型分篇，才能让「我遇到 X 现象该读哪篇」有唯一答案，编号 19–27 的顺序也因此是「最日常 → 最依赖前篇」的推进，而不是难度排名。代价与边界也很清楚：分组有重叠（证书与真机跨 23、24，协作与工程化跨 25、26、27），一篇覆盖不了某现象的全部侧面，需要顺着各篇「下一步」连读；另外 9 篇不是操作手册，具体命令与配置以各篇「可复制的配置」为准，本页只负责指路。

最小自验：拿「整站想切到本地、但 `/api` 要继续回源」这个现象，先在分组列找到「环境与路由」，确认它对应 19；再用五层法自问「这体现哪条原则」，从速查表里对上「顺序即优先级」。两张表能对上，说明地图已经会用了，全程不需要跑命令。

读这层时还有几处容易反过来想，先在这里点破，免得带着误解进正文：

- **容易以为 18–27 是「主线之后的进阶难度」，其实它是插在模块深潜与进阶实践之间的一组横向专题**，难度不必然更高，只是组织方向从「代码」换成了「问题」。
- **容易以为 9 篇要按编号顺序全部读完，其实每篇回答一个独立工程问题**，可以按现象跳读，只有各篇「下一步」链条才表示真正的依赖。
- **容易以为「可复制的配置」就是结论，其实配置只是五层里的现象与约束入口**，结论要走到「背后的设计思想 + 源码链路 + 边界与坑」才算完整。这几组对照也可以在 [《概念精解 · 易混淆概念辨析》](/concepts/08-confusions) 里找到更细的辨析。

六类分组不是六个并列抽屉，而是按「先解决什么、再解决什么」排的：环境与路由(19)、契约与模拟(20) 都在回答「目标怎么定」——一个把目标换成 dev server 或本地文件，一个干脆连目标都不需要；复现与回放(21)、故障与容错(22) 都在回答「怎么让偶现变必现」——一个把真实请求存下来反复打，一个把超时抖动注入成必现。同组两篇共享一个工程母题，差别只在手段，所以放在一起读比分开读省一半力气。

证书与真机(23、24) 排在后面，是因为它们要先补上「看不看得见」的前提：23 解决证书信任与 Tunnel to 排障，24 才谈手机流量怎么接进来、怎么在页面内调试。协作与工程化(25、26、27) 则收尾成一条链：配置怎么存与共享 → 怎么在 CI 里自动断言 → 哪里会撞上阈值与默认行为。越往后越依赖前面的机制，也越接近「把代理当工程设施」的视角；把这条推进顺序记住，编号就不再是需要背的序号。

分组是问题类型、篇是具体工程问题，所以一组可以含一到三篇：9 篇对应 9 个「我遇到 X 该读哪篇」的唯一答案，6 类只是给这 9 个答案归类。把这两个数字分清楚，就不会误以为「证书与真机」是一篇、或以为 6 类就该只有 6 篇；地图左列重复出现的分组名，正是在提示这种一对多关系。

若反过来按协议或模块分篇，地图会退化成功能清单：一个「HTTPS 页面证书不受信任」的现象牵涉 CONNECT 判定、证书签发、信任存储与界面提示好几块，读者仍要自己拼出该读哪几页，反查能力就没了。按问题类型分篇的代价是分组有重叠，收益是现象到篇目的映射唯一——这笔交换是本层刻意选的，也是它区别于模块深潜 13–17 的根本地方。

## 素材来源

本层的场景与规则全部有据可查，来源限定为三类，不引入外部臆测；结论与全站一致，以 `guide` 分支 `3b85cebc4`（v2.10.13）的源码为准，其后提交仅涉及文档站、业务源码零改动。

- **官方使用文档 `docs/docs/`**：`rules/` 100 篇、`gui/` 11 篇、`extensions/` 4 篇，加根下 `getting-started.md`、`faq.md`、`mobile.md`、`cli.md`、`index.md` 共 5 篇，合计 120 篇，提供规则写法、界面操作与官方明确的注意事项。
- **集成测试 `test/`**：`test/index.test.js` 与 `test/units/` 下 82 个 units，用来验证「某条规则真的会这样走」，例如 `test/units/composer.test.js` 直接向 `cgi-bin/composer` 连续 POST 构造请求。
- **真实 CGI 工作流 `biz/webui/cgi-bin/`**：文件名即接口名，例如 `get-data.js`、`get-matched-rules.js`、`sessions.js`，把界面上的一次点击对应到服务端的一段代码。

需要提醒的是，官方示例个别存在笔误：`docs/docs/rules/enable.md:82` 的 `www.example.com enale://https` 应为 `enable://https`（官方笔误，本站以正确写法为准），`docs/docs/faq.md:71` 又把 `w2 start` 漏成 `2 start`（应为 `w2 start`）。本站一律以源码为准：遇到文档与实现不一致时，先核对 `lib/` 下的解析逻辑，再决定规则该怎么写。「以源码为准」也是本层区别于官方使用文档的根本分工。

为什么这样设计：把来源限定为三类、且规定冲突时以解析逻辑裁决，是因为三者各有盲区——使用文档会滞后于代码、集成测试只覆盖被写到的那条路径、CGI 只暴露界面用到的接口；互相印证再落到实现，本站结论才不会随一处文档笔误漂走。上一段那两处官方笔误（`enale`、`2 start`）就是现成的反例：照抄文档会把规则写错，而以源码为准能立刻判出该用哪种写法。

代价与边界：以源码为准，意味着结论绑死在本站固定的那一版源码上；版本一变，位置、阈值与默认行为都可能失效，需要重新核对。这也是各篇「源码链路」给具体位置、而不只给模块名的原因——位置本身就是一条可复核的证据，读者能照着去看它是否仍成立。

类比：像判案时以法条原文为准，律师释义与既往判例只作佐证；释义里的错别字不能当成判决依据，文档与实现冲突时同理。

还有一处容易反过来想：**容易以为官方文档写了就能照抄，其实本层明确「以源码为准」**——120 篇文档与 82 个测试单元是素材而非结论，`enale`、`2 start` 两处笔误正是照抄会出错的现成反例，结论仍要回到实现核对一遍才算数。

三类来源的分工可以这样走一遍：官方文档先告诉你「支持什么写法」，集成测试再证明「这条写法真的会走这条路径」（例如向 cgi-bin/composer 连续 POST 构造请求），真实 CGI 则把「界面上的一次点击」对应到服务端的一段代码。三者对不上时，回到解析逻辑裁决——这条顺序让「有据可查」不止于引用，而是可复核，也和五层法里「源码位置」那一跳接得上。

官方示例会出现笔误，根源在于使用文档与实现由不同节奏维护：文档按发布节奏更新，解析逻辑随代码提交演进，个别行没跟上就会出现 `enale`、`2 start` 这类漏字。这也解释了为什么本站要把「以源码为准」写成分工，而不是顺手替官方改几个字——改字只修一处，定下裁决规则才能覆盖所有同类情况。

最后把本页与 9 篇正文的关系说清：18 给的是尺子（五层法、速查表、地图），19–27 是用尺子量具体问题；本页几乎不出现可直接复制的配置，不是省略，而是刻意把「怎么找」和「怎么配」拆开。读完若只想马上改一条规则，直接跳到对应场景篇即可，不影响理解——这也正是「横向专题」四个字的含义。

## 小结

- 新增这一层，是为了补上「会用规则」与「懂设计、能定位源码」之间的空白，方向与原有主线纵向递进互补。
- 追溯方法固定为五步：工程问题 → 设计原则 → 内核机制 → 源码位置 → 边界，文档结构与之逐一对应。
- 十条设计原则是本层的共用索引，既有「观测不改道」这类取值，也有「内存有界」「约定优于配置」这类工程约束。
- 9 篇文档按 6 类问题组织，场景来自 120 篇官方文档、82 个测试单元与真实 CGI 工作流，文档笔误以源码校正。
- 本篇为 [《本地联调与环境切换》](/scenarios/local-env) 准备了「用哪个视角读一个具体场景」：五层追溯法、十条原则速查表与 9 篇地图，19 是把它落到第一条真实规则上的第一站。
